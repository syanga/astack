# Claude router integration contract

This file records what PR1 established about the pinned CLIProxyAPI SDK, the
client protocol, the storage design, and distribution. It is the input to PR2
through PR6. The behavior contract is
[the routing spec](../../docs/specs/claude-account-routing.md).

Client evidence comes from terminal Claude 2.1.285 and
`@anthropic-ai/claude-agent-sdk` 0.3.276, the version in T3's lockfile. The Agent
SDK runs used the T3 adapter's query options. Under the user's 2026-10-04
decision on gate G2, those runs count as T3 evidence, and real T3 is checked
once at PR6 cutover. That decision supersedes the "T3 thread: blocked" wording
in the client evidence JSON files.

PR4's live session ran Claude Code 2.1.300 and Agent SDK 0.3.300
(`evidence/PR4/live-2-cc2.1.300/RESULTS.md`). PR4's fake-upstream session and
lane 2 were rerun on those versions with the same results, except for these
client changes (`evidence/PR4/fake-session-05ea0ee-cc2.1.300/`,
`evidence/PR4/lane-2-cc2.1.300/`):

- Claude Code 2.1.300 sends no `HEAD /api/hello` preconnect when nonessential
  traffic is off (see "Routes").
- After an SSE `overloaded_error` that follows `message_start`, with
  `CLAUDE_CODE_MAX_RETRIES=0`, it sends the request twice in all, not 4 times

- With thinking on, it adds `thinking.display: "updates"` to the body and the
  beta `thinking-display-updates-2026-08-18`. 2.1.285 sends neither. The router

- After a generic 400 to a thinking request, it sends the request once more

## How the router drives the SDK

These are the integration facts PR3 builds on. Each one is exercised by the
probes or read from the pinned source.

### Pinning

- A request-context value set by middleware never reaches the stock
  `POST /v1/messages` handler, because `ClaudeCodeAPIHandler` builds its
  execution context from `context.Background()`
  (`sdk/api/handlers/claude/code_handlers.go:238`). The stock count-tokens
  handler does the same (`code_handlers.go:122`).
- The probes pin through a router-owned route that calls
  `BaseAPIHandler.ExecuteStreamWithAuthManager` with `handlers.WithPinnedAuthID`.
  That route is the proven seam. Two other seams are plausible and unprobed: a
  custom `auth.Selector`, which still sees the Gin context, and
  `ExecuteModel` or `ExecuteModelStream` with an `AuthID`. Configuration apply
  replaces the selector (`sdk/cliproxy/service_config.go:216-218`).
- `api.WithRouterConfigurator` adds routes after the stock routes, which stay
  reachable and unpinned. The probes prove pinning on a distinct path, not
  interception of `/v1/messages`. PR3 serves the router on a distinct base path
  or behind its own front server, and closes or authenticates every stock
  route, including count-tokens.

### Attempt evidence

- The router's own transport is the evidence of an upstream attempt. The
  manager's round tripper provider receives every request the Claude executor
  sends, and the request carries the route's context. The probes set a call ID
  on that context, and the transport ties every attempt and its response
  headers to the call (`Upstream.AttemptsFor`).
- The selected-auth callback is a consistency check only. It fires on
  selection, before model resolution and auth preparation, and either can fail
  without an upstream request (`sdk/cliproxy/auth/conductor_execution.go:1043-1086`).
  A non-streaming refresh redispatch publishes no second callback
  (`conductor_execution.go:606-612`).
- A refused pin and an upstream 503 both reach the client as HTTP 503. The
  transport tells them apart: the refused pin has no attempt.
- The router's transport sees an attempt only when no proxy is in effect. The
  executor resolves one proxy URL from, in order, the request-level proxy in
  the execution options, the credential's `proxy_url`, and the global
  `requests.proxy-url` (`internal/runtime/executor/helps/proxy_helpers.go:127-138`).
  If any of them is set, the executor builds its own proxied transports and
  never calls the provider's round tripper
  (`internal/runtime/executor/helps/utls_client.go:399-416`). Attempts and
  paid-use headers would then bypass the router, which RP-17 and IO-6 depend
  on. PR3 enforces "no effective proxy at any level" (see the executor posture).
- With no proxy in effect, the Claude executor uses the provider's round
  tripper in place of its own uTLS transports for `api.anthropic.com`. The SDK
  does not export those transports. The provider accepted the router's
  transport in live use (row RP-18).
- The router's transport records whatever response it relays. The probe's fake
  transport records the scripted reply, so the header half of WC-7 compares the
  fixture with itself; the snapshot half goes through the SDK. PR3's transport
  wrapper reads `http.Response.Header` from the real response.

### Other integration facts

- `cliproxy.Builder.Build` replaces the core manager's round tripper provider.
  The probe sets its provider after `Build` and before `Run`.
- The SDK's Claude OAuth refresh and profile clients dial `platform.claude.com`
  and `api.anthropic.com` with their own uTLS transport. They ignore the
  manager's round tripper (`internal/auth/claude/anthropic_auth.go:189`).
- Account files in the SDK auth directory carry no `base_url`, so inference
  always targets `https://api.anthropic.com`. The probe serves that host in
  process through the round tripper and refuses every other host. No probe
  request left the process: every transcript records `refused_hosts: null`, and
  the evidence run also ran under a sandbox that denies non-loopback network.

## Executor posture

The router runs the SDK as a pinned executor that makes as few attempts as the
SDK allows, and owns every retry and migration decision.

| Setting | Value | Reason |
| --- | --- | --- |
| `routing.retry.request-retry` | `0` | With cooling disabled, SDK retry rounds retry the pinned account immediately, with no backoff. |
| `requests.streaming.bootstrap-retries` | `0` | Bootstrap retries also stay pinned, but hide pre-output failures from the router. |
| `routing.cooldown.disable-cooling` | `true` | With cooling on, one 503 blocks the pinned account. Later pinned calls fail without an upstream attempt. |
| `routing.session-affinity` | `false` | Stock affinity is in memory, model-keyed, and fails over when the bound auth is unavailable. |
| `routing.strategy` | any | A pin overrides every strategy tested. |
| `routing.retry.max-retry-credentials` | any | `0` means unlimited, but the scheduler filters candidates to the pinned ID. |
| `requests.passthrough-headers` | `false` | It does not affect error values. The router reads headers at its transport. |
| Proxy settings | none at any level | No global `requests.proxy-url`, no credential `proxy_url`, and no request-level proxy in execution options. Any of them bypasses the router's transport, so RP-17 attempt evidence and IO-6 paid-use detection would fail open. PR3 refuses to start or enroll when one is set. |

Limits of this posture:

- **A 401 can cost a second attempt.** If the credential has a refresh token, the
  SDK refreshes it and redispatches on the same auth whatever the retry
  settings say (`conductor_stream.go:253-263`, `conductor_execution.go:606-612`
  and `:818-824`, gated by `conductor_refresh.go:514-532`). Proxy-owned OAuth
  logins have refresh tokens. One attempt per call holds only for credentials
  without one (rows RP-5 and RP-5b). Pinning holds either way, and the
  redispatch passes the router's admission check like any other attempt
  (Routing loop).
- **Credentials can override the posture.** Credential metadata can override
  the global retry and cooling settings (`sdk/cliproxy/auth/types.go:466-483`
  and `:503-526`). PR3 refuses to enroll a credential file that carries such
  overrides.
- **The router owns backpressure.** With cooling disabled, the SDK dispatches to
  an account that just reported exhaustion
  (`TestPinnedExecutorPostureMakesOneAttemptPerCall/429-five-hour-rejected`).
  The router enforces account-wide concurrency and makes no attempt on a known
  exhausted account before its reset.

The SDK configuration is written once before `Service.Run` and never edited while
the service runs. To change it, restart the service. The
[data race section](#sdk-data-races) explains why.

## Failure classification

The router classifies a failure before output from per-call data only, as
implemented in `probes/classify.go`:

- the status code on the error the handler returns
- `IsRequestScoped()` and `IsCredentialScoped()` on that error
- the rate-limit headers of the call's own upstream attempt, captured at the
  router's transport

| Class | Signal | Router action (spec) |
| --- | --- | --- |
| `request_scoped` | Error is request-scoped, such as the SDK's fast-mode credit refusal | Report to the client, no retry |
| `transient` | 408 or 5xx, including 529 | Bounded retry on the assigned account |
| `network` | No HTTP response: the connection failed before the provider answered | Retry on a new connection on the assigned account, charged or not by phase ([Network failures](#network-failures)) |
| `throttle` | 429, not credential-scoped, no unified rejection in the attempt's headers | Bounded retry on the assigned account |
| `exhausted` | 429, credential-scoped or a rejected 5h or 7d window in the attempt's headers | Record exhaustion, migrate |
| `model_limit` | 429, unified rejection with only overage or model-specific claims | Record the rejection, which blocks the account for that model until its reset, as for `exhausted`. No provider response of this shape has been observed (row RP-14) |
| `auth` | 401 or 403 | Exclude from new placement, keep assignments |

The SDK's passive quota snapshot, `ModelStates[model].Quota.Signals`, is not a
classification source. It holds one snapshot per account and model. A response
with no quota headers leaves the previous snapshot in place
(`sdk/cliproxy/auth/quota_signals.go:26-46`). A headerless 429 after an
exhaustion therefore reads as exhausted from the snapshot
(`TestQuotaSnapshotOutlivesAHeaderlessFailure`). Concurrent responses on the
same account can also replace it before the router reads it. Status displays
that use the snapshot accept it only when its `ObservedAt` is at or after the
attempt start.

Qualifications:

- The ordinary Claude `statusErr` carries no response headers, so
  `ErrorMessage.Addon` is empty. Fast-request failures are the exception: they
  wrap a `RequestTerminatedError` that carries headers and body
  (`internal/runtime/executor/claude_executor_fast_error.go:94-98` and `:136-162`).
- `RetryAfter()` adds a random 1 to 30 second grace to a reset, and an
  overage-only rejection yields no retry duration. Exact resets come from the
  attempt's headers.
- The SDK can mark a 429 credential-scoped from a unified rejection without an
  explicit rejected 5h or 7d window (`helps/claude_ratelimit.go:28-41`).
- An in-stream `error` event is reported to the result policy as `Success: true`
  (`TestInStreamOverloadBeforeOutputIsDeliveredNotRetried`). PR3 owns the
  stream outcome state machine that classifies in-stream errors, premature
  EOF, and the completed-block boundary.
- No SDK interface reports the account's paid-overflow setting before a request.
  Overage headers arrive only on responses.
- The header names and values come from the SDK parser and synthetic responses.
  Real Anthropic header shapes for a rejection are still unobserved. The
  PR4 live session's 429s were injected by a local gate, not sent by the
  provider (`evidence/PR4/live-2-cc2.1.300/RESULTS.md`).

## Assignment storage

PR2 stores assignments in a single-writer, append-only JSON-lines journal.
PR1's `probes/journal.go` encodes the rules below. The service's journal,
`internal/router/store.go`, keeps them with its own record schema (see
"Assignment journal" under PR2).

- **Write rule.** `Assign` appends one record and calls `File.Sync` before it
  returns. A conversation's first record wins.
- **Fail-stop rule.** After any write or sync error, the journal acknowledges
  nothing more until it is closed, reopened, and recovered. A failed sync can
  leave a complete record on disk that the caller was never told about, so a
  later acknowledgment for the same conversation could disagree with replay.
- **Concurrency.** One mutex serializes first assignments in the process. An
  exclusive `flock` on the state directory refuses a second process.
- **Recovery.** On open, replay every complete line. Truncate a torn final line
  left by a crash or a failed write. Refuse to open when an interior line is
  corrupt or lacks a conversation or account, and report the error instead of
  reassigning.
- **Directory durability.** Creating the state directory syncs its parent.
  Creating the journal file syncs the state directory.
- **Durability scope.** Acknowledged assignments survive a process crash. OS
  crash and power-loss durability rely on Go's `File.Sync`, which issues
  `F_FULLFSYNC` on Darwin, falls back to `fsync` where the file system rejects
  it, and issues `fsync` on Linux. They are not tested.

A transactional embedded store, bbolt v1.5.0, also kept every acknowledged
assignment across the same kill -9 experiment. The journal was chosen because
it needs no dependency and its recovery rules are short enough to test
directly. The throughput figures in `evidence/PR1/storage/storage-comparison.json`
are not like-for-like and did not decide the choice: the journal answers
repeated conversations from memory, while bbolt opens a write transaction for
every call.

## SDK data races

The race detector reports data races inside the pinned SDK on three paths.

- **Configuration hot reload.** `Service.applyConfigRuntime` reaches
  `Server.UpdateClientsContext`, which writes `BaseAPIHandler` fields that
  request handling reads without synchronization. The race log reports
  `internal/api/server_reload.go:171`, `:189`, and `:190`, and
  `sdk/api/handlers/handlers.go:400` and `:411`. Pinned selection held in all
  20 runs. The race detector fired in 4 of 5 runs that sent requests right
  after the reload, and in none of the 5 runs that waited for account state to
  settle first. Prevention: the router writes the configuration once, keeps it
  private, and restarts to change it. The SDK watcher skips a configuration
  file whose hash is unchanged.
- **Auth updates.** `Manager.ReconcileRegistryModelStates` replaces
  `auth.ModelStates` under the manager lock, while `Manager.Update` clones the
  same stored auth after unlocking. The race appeared at startup in 1 of about
  35 probe starts that loaded accounts before `Run`. The same reconciliation
  runs on every auth update, including an added account and a rotated
  credential (`sdk/cliproxy/service_auth.go:343-348`). The SDK's own token
  refresh also writes the auth while the service serves.

- **Watcher startup.** The watcher's initial configuration apply
  (`Service.commitConfigUpdate`) writes the service configuration while auth
  registration reads it (`Service.oauthExcludedModels`). The probe at `6166c8c`
  hit this race when it wrote an account between `OnAfterStart` and the end of
  watcher startup (`evidence/PR1/unit-6166c8c/go.log`).

A production router starts with enrolled accounts in the SDK auth directory,
so the startup registration race and the watcher startup race are reachable there (row RP-20). The probes reduce the
races by starting with an empty auth directory, waiting for the SDK's "file
watcher started" log line, then adding accounts one at a time and waiting until
account state stops changing (`Probe.WaitQuiet`). `WaitQuiet` and the log-line
wait are test heuristics, not synchronization. The default suite passes under
`-race` with that order. The hot-reload probe sits behind the `sdkreload` build
tag. The PR3 service applies a rotation or account change only by restart,
and the SDK's own refresh ran in a live `-race` build with no race reported
(row RP-16). A router barrier on dispatch does not help with either race,
because the racing accesses are between SDK goroutines. A router-owned restart
to apply credential changes moves the rotation race into the startup race. An
upstream SDK fix closes both.

## Client contract

These decisions follow from the client evidence. PR3 implements binding,
delivered-output handling, the local 429, and the included-only controls. PR4
implements exhaustion waiting and migration (see "Recovery (PR4)").

### Bind conversations on the session header

- The binding key is `x-claude-code-session-id`. The router reads it from the
  raw client request, before any SDK rewriting, and cross-checks it against
  `metadata.user_id.session_id` in the body. All 803 captured requests carried
  the header, and it always equaled the metadata value
  (`identity-derived.json`, `identity_coverage_all_runs`).
- The key excludes `metadata.user_id.device_id` and `account_uuid`. The SDK
  rewrites both per credential (`sources/cliproxyapi-e2bff010/claude_credential_identity.go`).
- The key stays fixed across `--resume`, `--continue`, a model change, and a
  process restart (`identity.json#rows[0]`, `#rows[1]`).
- Subagents send the parent conversation's session id, so they inherit the
  conversation's account without a parent lookup. `x-claude-code-agent-id` and
  `x-claude-code-parent-agent-id` identify the agent tree
  (`identity.json#rows[2]`). Background subagents can still be in flight while
  their parent migrates. A dispatched request keeps its pinned account.
- A fork (`--fork-session`, T3 `forkSession`) carries no link to its origin, so
  the router treats it as a new conversation (`identity.json#rows[4]`).
- A request without the header, or whose header disagrees with the metadata
  value, gets HTTP 400 `invalid_request_error` with `x-should-retry: false` and
  a message that names the header. The router never places such a request on
  its own. The client evidence for this rule is an analogue: a 401 with
  `x-should-retry: false` made the client stop after one attempt
  (`runs/recovery-terminal-api-key-w-401-noretry`). PR3 tests the router's 400.

### Treat the first completed content block as delivered output

- A cut before the first completed content block makes the client discard the
  partial text and resend the identical request on the same session. The router
  may retry such a request on the assigned account (`recovery.json#rows[9]`).
- After a completed text block or `tool_use` block, the client keeps the output
  and sends a new continuation request. A completed tool ran once in every
  probe, including on resume (`recovery.json#rows[10]` to `#rows[13]`).
- Clients resend failed requests themselves, up to 11 attempts over about
  3 minutes, and `x-stainless-retry-count` stays 0 (`recovery.json#rows[0]` to
  `#rows[6]`). The router treats a resend as the same request for assignment and
  caps its own upstream attempts regardless of client retries.
- The router closes downstream streams gracefully. An abortive reset can drop
  frames the client has not read (`recovery.json`, `harness_notes`).
- After 300 s without bytes following `message_start`, the client resends the
  same messages with `stream: false`. The router accepts that request as the
  same conversation (`waiting.json#rows[2]`).

### Wait through a local 429 and the client's retry watchdog

- When no eligible account can serve a request, the router answers locally and
  makes no upstream attempt. The answer is HTTP 429 `rate_limit_error` with
  `anthropic-ratelimit-unified-status: rejected`,
  `anthropic-ratelimit-unified-reset` set to the earliest usable reset, and
  `retry-after` with the same delay. The message states the reset time.
- The router never uses spend-cap shapes such as `billing_error`,
  `out_of_credits`, or `org_spend_cap_reached`. The client watchdog fails at
  once on those.
- Managed client wiring sets `CLAUDE_CODE_RETRY_WATCHDOG=1`. With it, both
  clients sleep until the unified reset with no open connection, emit a
  countdown, cancel at once on SIGINT or `interrupt()`, and resume the same turn
  after the reset. One wait is capped at 6 h. With default settings, both
  clients stop at once on a reset longer than 60 s (`waiting.json#rows[4]`).
- For an unknown reset, the router omits `anthropic-ratelimit-unified-reset` and
  sends a bounded `retry-after` (`waiting.json#rows[5]`).
- The watchdog also raises client retries for other transient failures to about
  300. The router's cap on its own upstream attempts covers that, except for
  the 503 that ends a request whose last failure was a network failure,
  which clients retry ([Network failures](#network-failures)).

### Included-only: the documented limit is accepted

No supported interface prevents a paid request before dispatch
(`included-only.json`, `verdict`). The missing control is a provider-side,
per-request or per-credential guarantee that a request is served only from
included allowance. A request flag that rejects instead of drawing usage
credits would do, as would a documented, supported read of the account's
usage-credit setting with a freshness guarantee.

Under the user's 2026-10-04 decision on gate G1, the program accepts the
remaining limit. PR3 implements and tests these controls:

1. Read each account's overage state at enrollment. Refuse to dispatch to an
   account whose overage state is unknown or older than the freshness threshold
   PR3 sets.
2. Stop routing to an account the moment a response shows paid use
   (`representative-claim` overage or `overage-in-use: true`), and report it.
3. Name the remaining gap in the operating documentation: a paid request
   remains possible when usage credits are turned on outside the proxy after
   the last read, while the account's included windows are exhausted. The
   proxy sees that request only in its response headers.

Once implemented and tested, these controls satisfy the included-only gate for
live inference. Live inference still needs the user's attended login.

## Routing policy and assignment store (PR2)

PR2 adds the production policy and the durable assignment store in
`internal/router`, and the simulator in `cmd/claude-router-sim`. The simulator
calls the same `Router`; it has no second placement algorithm.

### Policy boundary

| Method | Effect |
| --- | --- |
| `Router.Decide(now, Request) (Decision, error)` | The policy. Reads assignments and account state, changes nothing. |
| `Router.Commit(now, Request, Decision) (Decision, error)` | Makes a `place` or `migrate` durable. It decides again under the commit lock and commits that fresh decision, which it returns. |
| `Router.Route(now, Request) (Decision, error)` | `Decide`, then `Commit`, before dispatch, in a loop of at most 3 attempts. PR3 calls this. |
| `Router.Report(Failure) Class` | Records a failure before output and returns the class the policy acts on. |
| `Router.Observe(account, attemptStart, Observation)` | Records the quota headers of one response. |
| `Router.Served(now, conv, account)` | Appends and syncs a mark that the conversation's current assignment has served a successful response. Written once per assignment. |
| `Router.ObserveOverage`, `Relogin`, `Move` | The paid-overflow check or observed paid use, relogin, and the manual override. |
| `Router.CommitAssignment` | Records an assignment without consulting the policy. For setup and tests only. |

Every method takes the current time, so the simulator drives production code
with a deterministic clock.

`Commit`, `Served`, `Relogin`, and `Move` share one lock. A `Served` or
`Relogin` call that lands between `Decide` and `Commit` is therefore seen by
the commit: a `never_served_relogin` migration decided before `Served` becomes
`reauth`, and one decided before `Relogin` becomes `dispatch`.

`Decide` returns one of these outcomes. Every outcome except `migrate` keeps
the assignment.

| Kind | When |
| --- | --- |
| `place` | A new conversation. Commit before dispatch. |
| `dispatch` | An existing assignment on a usable account. |
| `migrate` | Another account is eligible, and the assigned account has a known rejection that blocks the model (`exhausted`), showed paid use (`overage_observed`), needs login before the assignment served any response (`never_served_relogin`), or is no longer enrolled (`not_enrolled`). Commit before dispatch. A conversation whose account is no longer enrolled and that no account can take gets the `wait`, `refuse`, or `unavailable` of a new conversation and keeps its assignment (`TestAConversationOnAnAccountNoLongerEnrolledIsPlacedAgain`, `TestAConversationOnAnAccountNoLongerEnrolledKeepsItsAssignmentWhenNoAccountCanTakeIt`). |
| `retry` | `transient`, `network`, or `throttle` on the previous attempt, within `MaxAttempts`. |
| `fail` | The retry budget is spent, or the previous attempt failed `request_scoped`. |
| `wait` | No eligible account. `Until` is the earliest usable reset; `ResetKnown` is false when `Until` is only a recheck time. |
| `reauth` | The assigned account needs a browser login and the assignment has served a response, or no other account is eligible. |
| `refuse` | The included-only check fails for the assigned account and no migration applies, or it fails for every logged-in account when placing. `RecheckOverage` is set when a check is unknown or stale. |
| `unavailable` | No enrolled account is logged in. |
| `reject` | The request has no conversation identity. |

### Placement rule

Among logged-in accounts that pass the included-only check and have no known
rejection that blocks the requested model, `Decide` picks the account with the
smallest score:

```text
score = (active + 1) / (capacity * (1 + ResetBias * slack))
```

- `active` counts the account's conversations with a request or commit in the
  last `ActiveFor`, excluding the conversation being decided.
- `slack` is the largest `elapsed fraction - utilization` over the account's
  five-hour, weekly, and model windows that apply to the model, from an
  observation no older than `FreshFor`. A window counts only with a known
  utilization and a future reset. `slack` is 0 under `capacity_only` and for a
  stale or missing observation.
- Ties go to the earlier enrolled account.
- An account is blocked until the latest reset among its rejected windows that
  apply to the model. A five-hour reset therefore never unblocks an account
  whose weekly window is still rejected. A rejection with no reported reset
  blocks until `UnknownResetRecheck` after it was observed.
- Rejected windows accumulate across observations, in whatever order the
  observations arrive. A rejection stays until its reset, or until an
  observation stamped after it reports the same window, matched by kind and
  model scope in any prefix order, as not rejected. An observation that omits
  the window does not clear it. A rejection stamped before such an allowed
  report is not recorded. Utilization and freshness come from the newest
  observation only.
- Per window, the router keeps the newest rejection after it resets, when it
  no longer blocks, so that a delayed rejection stamped earlier is not
  recorded. Of two rejections stamped at the same time, the one that ends
  later is kept; a rejection with no reported reset ends
  `UnknownResetRecheck` after it was stamped.
- Merging an observation forgets the rejections that have reset by its stamp
  and were stamped at least one weekly period before it, and the allowed
  reports stamped at least one weekly period before it. Any evidence of the
  same window stamped earlier belongs to a window that has ended.
- The destination of every `migrate` is chosen by this rule.
- Reset preference affects only `place` and the destination of `migrate`.
  `Decide` never moves a healthy assignment, and a migrated conversation never
  returns on its own.

`Decision.Reason` is `reset_preference` when the reset-aware choice differs
from the capacity-only choice for the same request, and `capacity` otherwise.
`Decision.Observation` reports whether the chosen account's observation is
`fresh`, `stale`, or `absent`.

The comparison ran 13 variants over two synthetic fixtures and five seeds:
capacity-only, and reset-aware with bias 1, 2, 4, and 8 at freshness 5, 15,

quota and cache assumptions.

The selection criterion is the unused weekly share at reset, compared with
capacity-only on the same fixture and seed. `ResetBias` is the bias with the
largest mean reduction in that share. Bias 8 has the largest reduction at every
freshness on both fixtures. `FreshFor` is not chosen by the share. It is the
middle of the three swept values. At bias 8, 60 minutes had lower mean shares
than 15 minutes: 0.161 against 0.169 on `weekly-expiry-72h`, and 0.179 against
0.180 on `mixed-48h`. Both lowered the share against capacity-only in 9 of 10
seed runs, and 5 minutes in 8 of 10. The criterion does not require a lower
share in every seed run. Bias 4 at 60 minutes is the only variant that
lowered it in all 10 runs. Its mean shares are higher than the default's,
0.173 on `weekly-expiry-72h` and 0.183 on `mixed-48h`, and it writes fewer
migration cache tokens, 715,800 and 1,112,400 against the default's 846,800
and 1,358,200.

The cost was more cold cache writes from migration, and on `mixed-48h`

automatic migration, counting migrations returned to subagent requests. The
comparison does not establish a percentage improvement, and none is required.

### Quota evidence must come from the attempt

The SDK keeps its previous quota snapshot when a response carries no quota
headers, so a snapshot can predate the failure. `Report` treats `exhausted` and
`model_limit` as confirmed only when `Failure.Observation.At` is at or after
`Failure.AttemptStart` and the observation has a rejected window that applies
to the model. Otherwise `Report` returns `throttle`, records nothing, and the
next `Decide` retries on the assigned account. This matches the
classification above, which reads only the call's own attempt headers. PR3
supplies that evidence from its transport. For a credential-scoped 429
without a rejected window header, PR3 records an `unspecified` rejected
window observed during the attempt. A `request_scoped` failure ends the
request with `fail` and no retry, even if the account became exhausted in the
meantime.

`Observe` applies the same rule. It takes the start time of the attempt whose
response carried the headers, and ignores an observation stamped before that
time or with no time. PR3 passes the headers its transport captured for that
attempt, stamped with the response time.

### Included-only check

This is the policy side of IO-6. Each account carries a paid-overflow state
from `ObserveOverage`: `disabled`, `enabled`, or `paid_use`, with the time of
the check or response.

- **Observed paid use** counts as confirmed exhaustion of the account's
  included allowance. A conversation on that account migrates with reason
  `overage_observed` when another account is eligible. If none is, it waits
  for the earliest usable reset elsewhere or is refused with
  `paid_use_observed`, and keeps its assignment. New conversations skip the
  account. A migrated conversation does not return. While recorded paid use
  is in force, the transport sends the account no attempt, including the
  SDK's redispatch of a request that was waiting on a refresh.
- **Ordering.** The router records the latest check (`disabled` or
  `enabled`) and, separately, the latest paid use, each with its time. A
  check stamped before the latest recorded check is ignored. Of two checks
  stamped at the same time, `disabled` does not replace `enabled`. Paid use
  is in force unless the latest check is `disabled` and stamped strictly
  after the latest paid use. The outcome therefore depends on the stamps, not
  on arrival order:
  - A `disabled` check with the same time as the paid use does not clear it.
  - A delayed `disabled` check stamped before a newer `enabled` check does
    not clear it.
  - A later `enabled` check puts earlier paid use back in force, even after
    a `disabled` check had cleared it. Paid use at +1m, `disabled` at +2m,
    and `enabled` at +3m migrate the conversation with `overage_observed` in
    either arrival order of the two checks.
- **Unknown or stale check**, older than `OverageFreshFor`: `Decide` refuses
  dispatch with `overage_unknown` or `overage_stale`, sets `RecheckOverage`,
  and does not migrate.
- **Overflow enabled**: `Decide` refuses dispatch with `overage_enabled` and
  does not migrate.
- A new conversation is placed only on accounts that pass. When none pass and
  no account is waiting on a reset, it is refused with
  `no_included_only_account`. `RecheckOverage` is set if any account's check
  is unknown or stale.
- A `wait` also sets `RecheckOverage` when a logged-in account with no known
  rejection is held back only by an unknown or stale check, because a recheck
  could let it serve before the reset.

Precedence: confirmed exhaustion of the assigned account comes before its
overage state. A conversation whose account is exhausted migrates with reason
`exhausted` even when that account's own check is unknown or stale, because
the destination must pass the check: its latest check found overflow
`disabled` within `OverageFreshFor`. With no such destination, the
conversation keeps its assignment and gets `refuse` or `wait`. An unknown or
stale check alone never causes a migration.

PR3 owns the check mechanism and the documented remaining gap: usage credits
enabled outside the proxy while included windows are exhausted.

PR3 contract item (N11): paid use stamped before the latest check, when that
check is `disabled`, counts as cleared by it. PR3 must state its timestamp
rule for paid use, so that a paid-use response is never stamped earlier than
a `disabled` check the router already applied. Stamping paid use with the
response time, taken after the check completed, satisfies this. The
simulator fixtures assume a settings read every 15 minutes.

### Relogin before the first response

`Served` marks an assignment once it has served a successful response. The
mark is journaled, so it survives a restart, and a migration starts a new
unmarked assignment. When the assigned account needs a browser login:

- An unmarked assignment moves with reason `never_served_relogin` when another
  account is eligible. Otherwise `Decide` returns `reauth`.
- A marked assignment keeps the spec rule: `reauth` until relogin or a manual
  `Move`.

PR3 contract item (N13): PR3 calls `Served` for every successful response on
a binding, including responses to subagent requests, which share the
conversation's binding. The simulator does the same.

PR3 contract item (N4): PR3 must call `Served` and let it return before the
client sees the response complete. If PR3 cannot order it that way, it must
state why and what a crash between the two does. Such a crash leaves the
assignment unmarked, so a later relogin requirement could move a conversation
that has already served. PR3 also chooses the trigger: the first completed
content block or the end of the message.

### Assignment journal

The store is the single-writer JSON-lines journal from PR1,
`assignments.jsonl` in the state directory, with these PR2 rules.

- **Records.** `assign`, `migrate`, and `served`, each with conversation,
  account, and time. `migrate` also names its source. Replay applies the first
  `assign` per conversation, a `migrate` only when the conversation is on its
  source, and a `served` only when the conversation is on that account.
- **Fail stop.** As in the PR1 assignment storage rules above, after a failed
  write or sync the store returns `ErrFailed` until it is closed and reopened.
  That covers every path that could answer with an account: `Lookup`,
  `Decide`, `Commit` for every decision kind, `Route`, `Served`, `Relogin`,
  `Move`, and the shortcuts that return an existing binding without writing. The failed
  record may or may not be on disk, and replay decides which. No caller is
  told an account that replay can contradict.
- **Validation.** A commit with an empty conversation or account, or a
  migration without a source, fails with `ErrIncomplete` before anything is
  written. Replay refuses to open on an interior record that is not JSON, has
  an unknown op, or is incomplete in the same way. A torn final line is
  truncated.
- **Directory.** Creating the state directory syncs its parent directory.
- **Sync.** Go's `File.Sync` issues `F_FULLFSYNC` on Darwin and falls back to
  `fsync` when the file system does not support it.
- **Not durable in `New`.** A router made by `New` keeps quota observations,
  login state, paid-overflow checks, and conversation activity in memory.
  `Open`, which the service uses since PR4, keeps login state, known
  rejections, and paid-overflow state across restarts (see "Durable account
  state" under PR4). Conversation activity and utilization stay in memory.

## Local service (PR3)

PR3 adds the client-facing service in `internal/claude` and the
`claude-router` command in `cmd/claude-router`. The service calls the PR2
`Router` for every request. It has no placement logic of its own.

### Start sequence

`claude.Start(cfg, opts)` runs these steps in order and fails closed at each:

1. Validate the configuration. `listen` must be a loopback IP and port. The
   client token file must be mode 0600 and hold at least 32 characters.
   `LoadConfig` resolves a relative `client_token_file` against the
   directory of the configuration file, so the service and the commands read
   the same file from any working directory
   (`TestTheServiceReadsARelativeTokenPathBesideItsConfig`,
   `TestStatusFromAnotherDirectoryReadsARelativeTokenPathBesideTheConfig`).
2. Check every enrolled credential, `auths/<id>.json` in the state directory.
   It must be a Claude credential with an access token and mode 0600. After
   `coreauth.NormalizeCredentialMetadata` rewrites aliases such as `proxy-url`,
   it may hold only the keys the SDK's login and persistence write: `type`,
   `email`, `access_token`, `refresh_token`, `id_token`, `last_refresh`,
   `expired`, `refreshed`, `account_uuid`, `organization_uuid`,
   `organization_name`, `claude_device_ids`,
   `claude_account_profile_checked_at`, `skip_account_profile`, and `disabled`
   set to false. Any other key, such as `proxy_url`, `base_url`, or `headers`,
   refuses the start. The auth directory must hold no credential for an
   account that is not enrolled.
3. Open the assignment journal and build the `Router`.
4. Write `sdk-config.yaml` with the executor posture: request retry 0,
   bootstrap retries 0, cooling disabled, session affinity off,
   `max-retry-credentials: 1`, no proxy at any level. The SDK server listens on
   a private loopback port.
5. Run the SDK with a no-op watcher (`cliproxy.WatcherWrapper{}`). The SDK
   loads the enrolled credentials once, at start.
6. Wait for the SDK's watcher-step log entry, then until every enrolled
   account has an SDK auth with registered models and SDK account state has
   not changed for 250 ms.
7. Read each account's paid-overflow setting.
8. Open the client listener.

### Identity

`ResolveIdentity` reads `x-claude-code-session-id` from the raw request and
`metadata.user_id.session_id` from the body, in the JSON form and the older
`user_..._session_<id>` form. It answers 400 `invalid_request_error` with
`x-should-retry: false` when the header is missing, when the body has no

The model is the body's `model`, except that an alias the Anthropic API
accepts (`claude-sonnet-4-5`, `claude-haiku-4-5`, `claude-opus-4-5`,

ID it names. The SDK's model registry lists only the dated IDs and refuses an

ID, and per-model state treats both names as one model
(`TestModelAliasesTheAPIAcceptsAreServed`).

### Routing loop

For each routing step the service calls `Route`, which decides and commits
a placement or migration before it returns. A journal error answers 503. The service pins the SDK call with
`handlers.WithPinnedAuthID` and tags the context with a call ID that the
router's transport records. One routing step is one SDK call. With the
executor posture, one SDK call is one upstream attempt, except the SDK's
refresh redispatch (RP-5b).

| Decision | Answer |
| --- | --- |
| `place`, `dispatch`, `retry`, and `migrate` | Dispatch on the bound account. `Route` has committed a migration before it returns. When the request has already used its attempt cap, a `migrate` is answered with a local 429 whose reset is 1 s away, and the client's resend goes to the destination (PR4). |
| `wait` | Local 429 `rate_limit_error` with `anthropic-ratelimit-unified-status: rejected`, `anthropic-ratelimit-unified-reset`, and `retry-after` for the same delay. An unknown reset omits the reset header and sends `retry-after: 300`. |
| `refuse` or `wait` with `RecheckOverage` | Read the setting of the decision's account, or of every account when the decision names none, and decide again. A request reads each account's setting at most once (`TestWaitRereadsAnAccountWhoseSettingsReadFailed`) |
| `refuse` | 503 `api_error`, `x-should-retry: false`, naming the account and the reason |
| `reauth`, `unavailable` | 503 `api_error`, `x-should-retry: false`, naming `claude-router login`. An upstream 401 never reaches the client as 401. |
| `fail` | 503 `api_error`, `x-should-retry: false` |
| `reject` | 400 `invalid_request_error`, `x-should-retry: false` |

A failure before output goes to `Router.Report` with the class from
`classify`. It reads the status and headers of the call's last attempt at
the transport, and the SDK error's status and scope:

1. When the upstream answered that attempt with a 2xx status, the failure is
   the SDK's own. A request-scoped error is then `request_scoped` before any
   status check, so a generation the upstream already completed is never sent
   again. The SDK gives such an error status 500 when it carries none
   (`sdk/api/handlers/handlers_execution.go:358-361`).
2. When the attempt got no HTTP response, the failure is `network`, whatever
   the SDK's status and scope ([Network failures](#network-failures)). In fast
   mode the SDK marks every failure request-scoped, so this order retries a
   dropped connection (`TestFastModeConnectionFailureIsRetried`).
3. Otherwise the attempt failed with an error status, and the status decides
   first: 401 or 403 is `auth`, and 408 or 5xx is `transient`, whatever the
   SDK's scope. The attempt's own status wins when it is 400 or above. This
   order keeps an upstream 401 from reaching the client as 401 in fast mode.
4. Otherwise a request-scoped error is `request_scoped`. Either way it is
   answered at once with the upstream status and message and
   `x-should-retry: false`.
5. A 429 is `exhausted`, `model_limit`, or `throttle` from the attempt's own
   headers.

Transient, network, and throttle failures retry on the same account after
250 ms, then 500 ms, up to `MaxAttempts`.

One client request causes at most 4 upstream attempts. The router dispatches
at most 3 times, and the SDK can add one same-account redispatch after a 401
(RP-5b). The transport enforces the cap: it refuses a fifth attempt before
sending it, and the service answers 503. It also refuses an attempt for any
account but the one the call is pinned to. Before a response reaches the
client, the service checks that the transport saw at least one attempt for
the call, all on the pinned account, and otherwise answers 502.
`max_upstream_attempts` lowers the cap to 1, 2, or 3. With 1 the router
never resends a request that may have reached the provider, so upstream
attempts equal client requests; the live lane uses this
(`TestASingleAttemptCapNeverRetries`). A network failure before the request
was written is not an upstream attempt, and the router retries it under any
cap ([Network failures](#network-failures)).

The transport also refuses an inference attempt, the SDK's refresh
redispatch included, when the router would not dispatch to its account at
that moment (`Router.Admit`). That is the case when the account needs a
login, showed paid use, has a rejection that applies to the model, or has no
`disabled` check within `OverageFreshFor`. After a journal write or sync
failure it is the case for every account. The transport does not check
settings reads. `Admit` takes the lock under which the router records
observations, so each check falls wholly before or wholly after each
observation. The transport refuses an attempt whose check comes after a
blocking observation. An attempt whose check came first is sent, even if the
observation is recorded while it is in flight. A refused attempt reaches no
upstream and does not count toward the cap.

After a refusal the service logs `attempt_refused` with the reason, reports
no failure to the router, and decides again. The client gets the answer the
table above gives for that decision. For each reason `Admit` returns:

- `paid_use_observed`: a migration for `overage_observed` when another
  account is eligible, a local 429 until the earliest usable reset elsewhere,
  or a 503 that names paid use. When another account's check is unknown or
  stale, the refusal sets `RecheckOverage`, and the service first reads the
  paid-use account's setting once. If the read returns `disabled` stamped
  after the paid use, the paid use is no longer in force, and the request
  goes out on the same account
  (`TestPaidUseRecheckClearedByADisabledReadingServesOnTheSameAccount`).
- `exhausted`, which also covers a model-limit rejection: a migration for
  `exhausted` when another account is eligible, otherwise the local 429, or
  a 503 when the paid-overflow state bars every logged-in account.
- `needs_login`: a migration for `never_served_relogin` when the
  conversation was never served and another account is eligible, otherwise a
  503 that names `claude-router login`.
- `overage_unknown` or `overage_stale`: one read of the setting, then
  another decision. The request dispatches if the read returns `disabled`
  and otherwise answers 503. A request reads each account's setting at most
  once.
- `overage_enabled`: a 503 that names the account and paid overflow.
- `journal_failed`: the 503 for a journal error, because the next decision
  fails on the journal too.

`TestRefreshRedispatchIsRefusedAfterABlockingObservation` covers paid use
and exhaustion on the streaming and non-streaming paths,
`TestRefreshRedispatchIsRefusedAfterTheJournalFails` covers a journal
failure on both, and
`TestRefusedRedispatchMovesTheConversationAfterPaidUse` covers the
migration. The admission check reads both clocks as the policy does, so
`Admit` and `Decide` agree during a hold
(`TestAdmitAgreesWithDecideDuringAHold`). A resend
after a backward step of the wall clock is refused with `overage_stale` and
reaches no upstream
(`TestRefreshRedispatchAfterABackwardClockStepIsRefusedAsStale`).

The cap is per client HTTP request. Every router-made HTTP failure answer
carries `x-should-retry: false`, which a client honors, except the 503 that
ends a request whose last failure was a network failure
([Network failures](#network-failures)).
Two other answers do not
stop client retries: an SSE `error` event after the response committed,
which Claude Code retries for `overloaded_error`, and the local 429, which
clients wait through and resend. Each resend is a new request with its own
cap. `CLAUDE_CODE_MAX_RETRIES=0` stops the client's HTTP retries but not its
resend after an SSE `overloaded_error`. The number of requests in all depends
on the client version and on the case:

| Case | Claude Code 2.1.285 | Claude Code 2.1.300 | Agent SDK |
| --- | --- | --- | --- |
| Error right after `message_start`, `CLAUDE_CODE_MAX_RETRIES=0`, watchdog off (`evidence/PR4/client-probe-2.1.300/`) | 4 (3 streaming, 1 non-streaming) | 2 (1 streaming, 1 non-streaming) | Not measured |
| Error after a `ping`, behind the router, default retries, watchdog on (`ping_error_resends` in `evidence/PR4/lane-2/recovery.json` and `evidence/PR4/lane-2-cc2.1.300/recovery.json`) | 4 (3 streaming, 1 non-streaming) | 4 (3 streaming, 1 non-streaming) | 4 (3 streaming, 1 non-streaming) with 0.3.276 and with 0.3.300 |

The two cases differ in both the event before the error and the client
settings, so the cause of 2.1.300's lower count in the first case is not
isolated. A caller that needs a bound across requests counts requests in
front of the client, as the live runbook's gate does.

The router retries only a failure before output: an error status, an error
event before any other event, or a connection that dropped before the first
event. In the first two the upstream sent no output. A connection that drops
after the request was written, outside fast mode, may have dropped after the
upstream began generating, and the retry can make it generate twice for one
client request. Delivery of a dropped request is therefore at least once, not
exactly once. A request-scoped SDK error after a 2xx attempt is final (rule 1
above).

### Network failures

A network failure is an attempt that got no HTTP response: a refused or
timed-out connection, a failed TLS handshake, or a connection reset or
closed before the response headers arrived. The service classifies it
`network` and records its phase from the hooks net/http calls
(`net/http/httptrace`):

| Phase | When | Provider may have run it | Charged to the attempt cap |
| --- | --- | --- | --- |
| `before_write` | No connection was obtained, every write of the request failed, or the transport canceled the try at the end of the network retry time before net/http read the whole request body | No | No |
| `after_write` | Anything else, including a connection on which net/http reported no write, and a canceled try whose whole body net/http had read | Yes | Yes |

net/http's HTTP/2 transport reports no write when writing the headers fails,
so a header-write failure is `after_write`. A stream whose request net/http
reported written before its HTTP/2 connection was force-closed is
`after_write` because of that report. Both retry within the attempt cap, and
a request whose retries run out on one of them ends with the retryable 503
described below.

The transport retries a `before_write` failure itself, without returning to
the SDK. It waits 250 ms, then 500 ms, 1 s, and 2 s for each later try. The
network retry time starts at the request's first `before_write` failure and
ends when either the monotonic clock or the wall clock has advanced 25 s
since then. A backward step of the wall clock therefore does not extend it,
and time the machine slept, which the monotonic clock omits, still counts.
After each wait the transport reads both clocks and starts no try after that
end. Each try checks `Router.Admit` and the cap again. A client that goes
away ends the retries.

A try has no time limit of its own. Once the network retry time has started,
the transport cancels every try of the request that is still unwritten when
the time ends, including a try the routing loop starts after an
`after_write` failure. A try is unwritten until net/http reports its write or
the first byte of a response arrives, including a 1xx response. That covers
a dial, a TLS handshake, and a body write that an HTTP/2 server stalls by
granting no flow-control window. The transport cancels at the end of the
time. When the machine sleeps or the wall clock steps forward past the end,
it cancels within 1 s of the wake or the step. After the end, the next
`before_write` failure ends the request. A canceled try is that failure
unless it counts as `after_write`, as the next paragraph describes. The
routing loop retries an `after_write` try if the cap allows, and the
transport cancels each later try of the request before net/http starts it.
A try that fails with its own error just as the time ends is not a canceled
try. It keeps its error and its phase.

net/http's HTTP/2 transport can return from a cancel before it reports a
write, even after it sent the last byte. The transport therefore counts a
canceled try as `after_write` and charges it when net/http had read the
whole request body. This charge is conservative. It also charges a try whose
last bytes were still waiting for flow-control window, so the provider never
received the whole request. A cancel can also reach a request whose last
byte was sent before net/http reported the write. That request is charged,
and the routing loop retries it as an `after_write` failure, so the provider
may run it twice. The error text of an uncharged canceled try says that the
request was not written, and that of a charged one says that the request may
have been written.

The transport never cancels a try that net/http reported written or whose
response began. Such a try waits for the provider or for a network failure,
so the network retry time bounds only the tries that are unwritten when it
ends. A try that starts before the request's first `before_write` failure has
only the 10 s dial timeout and the 10 s TLS handshake timeout, so its body
write can stall without a bound.

When the network retry time runs out, the `request` event has `reason:
provider_unreachable`, and `claude-router status` shows the conversation as
`provider unreachable`.

An `after_write` failure returns to the routing loop, which retries it like a
`transient` failure: on the assigned account, after 250 ms and then 500 ms,
within the attempt cap. A network failure changes no account state, so it
never migrates a conversation. When the cap is spent, the `request` event has
`reason: retry_budget_spent`.

A request whose last failure was a network failure ends with 503
`api_error`, `x-should-retry: true`, and `retry-after: 5`, whether the
network retry time or the attempt cap ended it. When the network retry time
ended it, the message names the last error. Every other request that spends
the cap, such as one whose last failure was a provider 5xx or a throttle,
ends with the cap's 503 and `x-should-retry: false`.

Claude Code 2.1.300 and Agent SDK 0.3.300 retry that answer up to 10 times.
Without `retry-after` they back off about 0.5 s and then 1.1 s. With
`retry-after: 3` both waited 3 s before each retry. A wait of 5 s for the
router's `retry-after: 5` follows from that but was not observed. Claude Code
with `CLAUDE_CODE_RETRY_WATCHDOG=1` retries up to 300 times. Both clients
stopped after one request only when the 503 carried `x-should-retry: false`.
Status 500, 503, or 529, and error type `api_error` or `overloaded_error`,
made no difference. Each client retry is a new request with its own cap and
its own 25 s.

After any network failure the transport replaces its `http.Transport` with a
new one and closes the old one's idle connections. Later attempts therefore
dial new connections and never reuse the one that failed. Requests already in
flight on the old transport finish on it. Several streams that fail together
on one HTTP/2 connection cause one replacement.

Each network failure is an `attempt_failed` event with `class: network`, its
`phase`, the error text in `detail` (at most 200 bytes), and no `status`.
The transport logs the failures it retries too. The `request` event's
`upstream_attempts` counts only charged attempts.

A failure after the response headers arrived, such as a stream that drops
before its first event, is not a network failure. It keeps its class, and
the transport does not replace its `http.Transport` for it.

The retryable answer has two costs. First, an `after_write` retry, by the
router or by the client, can make the provider run one client request twice,
and each run draws on the account's allowance. Second, client retries
multiply attempts. One prompt that ends this way 11 times, the first request
and 10 client retries, can cause up to 44 upstream attempts with the default
cap of 4 and 11 with a cap of 1. With the watchdog's 300 retries the bounds
are 1204 and 301. These are upper bounds. The router dispatches at most 3
times per request (`MaxAttempts`), so a run of `after_write` failures usually
ends after 3 attempts, 33 for 11 requests. Only the SDK's redispatch after a
401 adds a fourth.

### Streams

The service holds the response until the first complete SSE event. An
`error` event first is a failure before output: `overloaded_error` and
`api_error` are transient, `rate_limit_error` is throttle. An event without
an `event:` line takes its name from the `type` field of its data, so a
data-only error counts too. Any other first event, including `ping`,
commits the response. An error after a `ping` therefore reaches the client,
which retries it itself (`recovery.json`). After that the service relays every chunk,
writes an `error` event if the SDK fails or if the stream ends without
`message_stop`, and returns, which ends the chunked response cleanly. A client that goes away cancels the SDK call. The stream
`stop_reason` and `message_stop` are relayed as received. A `stream: false`
request, including the client's 300 s fallback, is the same conversation.

### Served mark

The service calls `Router.Served` for every successful response on a
binding, subagent requests included: at the first `content_block_stop` of a
stream, at `message_stop` for a stream without a content block, and before
writing a non-streaming response. This answers PR2 item N13 (`TestSubagentSuccessMarksTheAssignmentServed`).
This is the boundary where clients keep output (`recovery.json#rows[9]` to
`#rows[13]`). `TestServedMarkFollowsTheFirstCompletedBlock` shows a cut
before the first completed block leaves the assignment unmarked.

This answers the N4 item above. The service scans each chunk before writing
it, and `Served` returns, with the record synced, before the chunk that holds
the first `content_block_stop` reaches the client. A non-streaming response
is written after `Served` returns. A crash therefore cannot leave a completed
block on the client with an unmarked assignment.
`TestServedMarkIsOnDiskBeforeTheClientSeesTheCompletedBlock` reads the
journal at the moment the client sees the block. If `Served` fails, the
client gets an SSE `error` event in place of the completing chunk, or a 503
for a non-streaming request, and the journal stops answering until restart
(`TestServedMarkFailureStopsTheCompletedBlock`).

### Paid-overflow reading

The service reads `extra_usage.is_enabled` from
`GET https://api.anthropic.com/api/oauth/usage` with the account's SDK
credential (`Manager.NewHttpRequest`) through the router's transport. It
sends `anthropic-beta: oauth-2025-04-20` and makes no inference request.
`is_enabled: false` is `disabled`, `true` is `enabled`, and any other answer,
including a missing `extra_usage` or a 401 that survives a refresh, leaves
the state unknown, and an unknown state is refused. A usage-read 401 does not
mark the account as needing login, because only a restart would clear the
mark.

A read never uses an access token that the SDK is about to replace. The SDK
revokes the old access token when it refreshes, so a read that races the
SDK's refresh gets 401. The live lane hit this race on a start with an
expired credential. When the credential expires within the SDK's refresh
lead (4 hours for Claude, the SDK's own test in `Manager.shouldRefresh`), or
the usage endpoint answers 401, the read renews the credential:

- If the SDK already installed a newer access token, the read uses it.
- If the SDK has a refresh pending (`NextRefreshAfter` in the future), the
  read waits up to 3 s for it. If the refresh lands, the read uses the new
  token. If its exchange fails, the read fails. If it is still running after
  3 s, the read fails and a re-read follows (below).
- Otherwise the router refreshes through the SDK
  (`Manager.ForceRefreshAuth`), which takes the SDK's per-credential refresh
  lock.

The router registers a refresh guard in place of the SDK's Claude executor
before the start reads. The SDK calls the executor's `Refresh` for every
refresh, its own and the router's, while it holds the credential's refresh
lock, and hands it the credential as it is at that moment. The guard
records, per credential, the last 8 refresh tokens an exchange sent and did
not get back, and marks those whose exchange failed or ended unknown. A
refresh the router started carries the access token the router decided on.
The guard declines it, with no exchange, when the credential's access token
has changed since then or its refresh token is recorded. The decline is a
`context.Canceled`, for which the SDK records no failure and no backoff. The
router then reads the credential again: a new access token counts as the
SDK's refresh, and the same one starts a failure run. The SDK's refresh of
a credential that is due at start can begin before the guard exists, on the
executor the guard replaces. So a credential with a refresh marker
(`NextRefreshAfter` set) when the guard is registered has its refresh token
recorded, and one whose refresh already failed has it recorded as failed.
The SDK sets the marker 60 s ahead when it queues an auto-refresh and
changes it only when that refresh finishes, so a refresh whose exchange
outlives the 60 s, as after a start stalled that long, still has its marker
(`TestSDKRefreshThatBeganBeforeTheGuardAndOutlivedItsMarkerIsNotResent`).
The marker can also be the SDK's 30 s pause after a refresh that returned a
token that is still due. The SDK refreshes that token again after the
pause, so recording it costs at most failed reads until that refresh lands.
For a refresh the guard did not see, the SDK's failure record on the
credential (`LastError`) tells the router that it failed. While that credential's old token is current its
reading stays unknown, so no inference runs on the account, and a failure
record can only come from the refresh.

**The router never sends a refresh token that an earlier exchange sent and
did not get back.** That covers a token whose exchange failed or ended
unknown, and a token whose rotation the SDK did not install. It holds in
every interleaving with the SDK's refreshes in which two properties hold:
every refresh takes the SDK's per-credential refresh lock and then looks up
the registered Claude executor, and the guard is that executor. The check
then runs under the lock on the credential the exchange would send. The
SDK's own refreshes pass the guard unchanged: its auto-refresh retries a
failed refresh token after its backoff, and its request-time 401 path
refreshes without a pending marker.

If the SDK registers a new Claude executor in place of the guard, the
router stops refreshing and its reads of a due or refused credential fail.
The router checks the registration after the start reads and before each
refresh it starts, and logs `refresh_guard_replaced` the first time it
finds the guard replaced. The check before a refresh is not atomic with the
SDK's executor lookup: a replacement between the two lets that one refresh
run without the guard. With the router's SDK configuration, only the SDK's
startup model sync registers a Claude executor once the SDK has started,
and it runs during the startup quiet period (row RP-20). The user has not
accepted this gap (P2b). Closing it needs a check that is atomic with the
SDK's executor lookup, which the pinned SDK does not offer.

The guard forwards the Claude executor's refresh, request, and request
preparation methods, but not `ForAPIKey`. The SDK calls `ForAPIKey` only
for an API-key credential (`executorForAuth`), and the router enrolls OAuth
credentials only, so the SDK never needs it here.

A failed refresh, the router's or the SDK's, starts a failure run that lasts
until the access token changes. The guard reports the SDK's failures. During
the run a read fails at once: it neither waits for the SDK nor refreshes,
and the SDK's own retries pace the next exchange. So the router starts at
most one refresh per failure run, the one that starts it, and none when the
SDK's refresh failed first. An inference error the SDK records on the
credential does not start a run.

The rule has one cost. When an access token is refused (usage 401) before it
is due, and a refresh of it fails or ends unknown, the router's or the
SDK's, nothing refreshes it until the token enters the SDK's 4-hour lead:
the SDK does not refresh a token that is not due, and the router does not
resend the refresh token. Until then the account is refused once its
reading goes stale, unless an inference request that the fresh reading
still allows gets a 401 and the SDK's request-time refresh renews the
credential. For an 8-hour token the outage lasts under 4 hours, plus the
SDK's refresh and the next read (up to `overage_check_every`). The user has
not accepted this cost (L2).

One read sends at most two usage requests and starts at most one refresh.
A refresh is one call to the executor's token exchange, which posts to the
token endpoint up to 3 times on transport errors and 5xx answers, 1 s and 2 s
apart. The SDK gives each post its own 30 s timeout. The router's 30 s cap on
its own refresh stops further posts but not one in progress. Neither cap
covers the wait for the SDK's per-credential refresh lock: a refresh the
router starts while the SDK refreshes the same credential without a pending
marker (the SDK's request-time 401 path, or an auto-refresh whose exchange
outlives its 60 s marker) waits for that refresh, which can hold the lock
for about 93 s with three slow posts. So a read has no fixed wall-clock
bound. The start reads' 15 s limit ends their waits and usage requests, but
not a refresh in progress.

Each refresh the router starts, each SDK refresh that a read waited for or
found, and the first failure of a failure run record a `credential_refresh`
event with its reason (`expiring` or `unauthorized`) and outcome
(`refreshed`, `sdk_refreshed`, or `failed`). A failure of the SDK's refresh,
or a refresh the guard declined on a spent token, carries the detail
`sdk refresh`. The event carries no token and no error text
(`TestReadOfADueCredentialWaitsForTheSDKRefresh`,
`TestReadDoesNotRefreshWhileTheSDKRefreshIsRunning`,
`TestRouterRefreshesADueCredentialTheSDKHasNotQueued`,
`TestReadThatRefreshedDoesNotRefreshAgainAfterA401`,
`TestUnauthorizedReadUsesTheTokenTheSDKInstalledDuringTheRead`,
`TestUnauthorizedSettingsReadRefreshesOnceAndReadsAgain`,
`TestFailedSDKRefreshIsNotRepeatedByReads`,

`TestRouterRefreshQueuedBehindAFailingSDKRefreshSendsNoExchange`,

`TestDueReadUsesTheTokenTheSDKInstalledWhileItWaitedForTheLock`,

A failed read (an error status, a transport error, an unreadable answer, a
failed refresh, or a 401 after the refresh) schedules a re-read. After the
n-th failed read in a row, scheduled or on demand, the next scheduled read
comes 5 s x 2^(n-1) after it, or after the endpoint's `Retry-After` when
that is longer, capped at half of `overage_check_every`. A run of failed
reads adds at most 6 re-reads. After them the account is read once per
`overage_check_every` until a read succeeds. A success, scheduled or on
demand, ends the run, and the next scheduled read comes one
`overage_check_every` after it. With the defaults, the re-reads come 5, 10,
20, 40, 80, and 160 s apart, and an account sends at most 14 usage requests
and starts at most 7 refreshes in the 10 minutes after a failed read, then
at most 2 usage requests and 1 refresh per 10 minutes. During a failure run
of refreshes the router starts none after the first. On-demand reads add at
most one read per 30 s while a request waits on the account
(`TestRateLimitedStartReadIsReadAgainAfterRetryAfter`,
`TestPersistentUnauthorizedReadStaysUnknownWithBoundedReads`,
`TestSuccessfulRecheckEndsTheRunOfFailedReads`,
`TestFailedRecheckBringsTheReRead`). The live lane got 429 on
the seventh start in 40 s; before this schedule, the account stayed unknown
until the next 10-minute read. During the PR4 live step W6, the upstream gate
could not resolve the provider's host and answered the reads of both accounts
with 502. The re-reads came 5, 10, 20, 40, 80, and 160 s apart. A later
read succeeded before the waiters sent again
(`evidence/PR4/live-2-cc2.1.300/W6/upgate.jsonl`).

Timestamp rule (PR2 item N11): the upstream makes a reading at an unknown
time between the start of the read or attempt and its arrival. A `disabled`
reading, which allows dispatch, is stamped with that start. An `enabled` or
paid-use reading, which blocks dispatch, is stamped with its arrival. This
applies to settings reads and to response headers alike. Under PR2's ordering
rules (the latest check wins, and paid use clears only on a `disabled` check
stamped strictly after it), a `disabled` reading supersedes blocking evidence
only when its read or attempt started strictly after that evidence arrived.
Overlapping readings resolve toward blocking: an `enabled` reading that
overlaps a `disabled` one is ordered after it, even when the upstream made
it first. Examples:
- A `disabled` response or read that started before a paid-use response
  arrived does not clear the paid use, even when it arrives later
  (`TestDisabledResponseFromAnAttemptStartedBeforePaidUseDoesNotClearIt`).
- An `enabled` settings read in flight outranks a `disabled` response from
  an attempt that started during the read
  (`TestEnabledSettingsReadInFlightOutranksAnEarlierDisabledResponse`).
- Paid use is stamped at its arrival, so only a `disabled` read that started
  after it arrived can clear it, whatever order the router applies the two
  in. The router can apply a `disabled` reading first while the paid-use
  response is still on its way to `ObserveOverage`.

Every stamp the service passes to the router (`Observe`, `ObserveOverage`,
and the attempt start in `Report`) comes from the service clock, read at the
start of a read or attempt or at an arrival. It is never zero and never
later than the clock at the time of the call. The service clock is wall time
without Go's monotonic reading and never moves backward, so a wall-clock step
back does not reorder readings (PR4, "Wall time across sleep"). The
service enforces the rule at the boundary (`Service.bounded`), because PR2
misorders readings otherwise: a future stamp sweeps a live rejection or
clears paid use, and paid use stamped with the zero time is dropped. The
service checks a reading's start and arrival stamps together. When either
breaks the rule, a blocking reading (paid use, `enabled`, a rejection, or a
failure report) is kept and stamped with the current time at both ends,
which is no earlier than the reading. A reading that only permits dispatch
(`disabled`, or windows without a rejection) is dropped. Both cases record a
`stamp_bounded` event
(`TestObservationsReachTheRouterStampedNoLaterThanNowAndNeverZero`).

Observed paid use does not expire (PR2 at `22d4342`): a later `enabled`
check puts it back in force after a `disabled` check cleared it.

A refusal for an unknown reading names each failed settings read and the
login command, because a revoked login shows up only as a failed read.

Every upstream response also reports the setting at the time it was served.
The transport feeds it to `Router.ObserveOverage` before the SDK reads the

## Recovery (PR4)

PR4 replaces PR3's local 429 for an exhausted conversation with migration,
keeps account state across restarts, and adds the manual override. The
policy is PR2's, except for the stale-check rule in "Waiting".

### Wall time across sleep

Go's monotonic clock stops while macOS sleeps (and during Linux suspend), and
`time.Time` comparisons use it when both times carry it. On that clock, a
`disabled` reading taken 5 minutes before a 2-hour sleep would still count as
5 minutes old after the wake, so the router could dispatch on a reading that
was stale by wall time.

- **The service clock is wall time.** The service strips the monotonic
  reading from every time it takes, so every stamp it gives the router and
  every `now` the policy compares against is wall time: overage freshness,
  the order of checks and paid use, unknown-reset rechecks, and request
  times. The saved account state already held wall time only, so one rule
  applies before and after a restart. The clock never returns a time earlier
  than one it returned. After a backward wall-clock step, it stands still
  until the wall clock passes the last time it returned, so a later reading
  is never stamped before an earlier one
  (`TestThePolicyComparesStampsWithoutAMonotonicReading`,
  `TestTheServiceClockNeverStepsBackAndExpiresOldChecksWhileItHolds`). The
  rest of this section calls that period a hold. A raw wall clock would let
  a step reorder readings. It could stamp an `enabled` reading taken after
  the step before a `disabled` check taken before it, and `ObserveOverage`
  would then ignore the `enabled` reading.
- **A hold expires every `disabled` reading.** A clock that stands still
  cannot age a reading. The clock therefore calls
  `Router.ExpireOverageChecks` at each backward step of the wall clock,
  after each `overage_fresh_for` of wall time in a hold, and when the hold
  ends. It passes a time later than every time it returned before, and it
  makes the call before it returns that time to any caller. The router then
  counts every `disabled` check stamped before that time as stale. The next
  request to the account reads the setting again, even within 30 s of the
  last read. It dispatches only on a `disabled` reading from a read or
  attempt that started after the call. When that read fails, the request is
  refused with `overage_stale`
  (`TestAfterTheWallClockStepsBackNoRequestDispatchesOnAnOldReading`). Any
  backward step expires the readings, however small. It costs one settings
  read for each account the next requests use. On macOS, `timed` slews
  small offsets without stepping, so a step usually comes from a manual
  clock change or a large correction. Requests that read the clock at the
  same time never see a step that the wall clock did not take
  (`TestConcurrentCallersOfAForwardWallClockNeverExpireChecks`).
- **A restart keeps only a `disabled` check it can age.** After a restart,
  the router ages a saved check by the wall clock. `accounts.json`
  therefore holds no `disabled` check during a hold, and none stamped
  before the time of the last `ExpireOverageChecks` call. The saved records
  of accounts left out of the configuration follow the same rule. Each call
  removes those checks from the file before the clock returns its time. The
  next start then reads the setting before it dispatches to the account,
  including an account that returns to the configuration
  (`TestAnAccountLeftOutWhileChecksExpireReadsItsSettingWhenItReturns`). A
  restart without a step keeps the saved check
  (`TestAfterARestartNoRequestDispatchesOnAReadingOlderThanItsFreshness`).
  A `disabled` reading therefore never permits dispatch more than
  `overage_fresh_for` after its read started. The limit applies during a
  hold, after it, and across a restart, except after a backward step of the
  wall clock while the router is stopped.
- **Resets are compared with the wall clock.** The policy takes both clocks
  (`router.Instant`). It ages readings and stamps bindings with the service
  clock, and it compares reset times with the wall clock. An exact reset is
  the provider's wall time, so a hold cannot make a future reset count as
  past. The router moves the conversation or waits, as it does without a
  step (`TestAfterTheWallClockStepsBackAFutureResetStillMovesTheConversation`).
  A rejection without a reported reset ends `UnknownResetRecheck` after its
  service-clock stamp. During a hold that stamp is ahead of the wall clock,
  so the rejection blocks longer, never shorter. The local 429's
  `retry-after` counts to the reset on the wall clock too
  (`TestAfterTheWallClockStepsBackTheLocalWaitCountsToTheResetOnTheWallClock`).
- **A step while the router is stopped is not detected.** At the next start,
  the router drops a saved `disabled` check stamped later than the wall
  clock. It keeps an earlier one, which then counts as younger than it is by
  up to the step. The start reads every account, and a successful read
  replaces the saved check. The error remains only for an account whose
  start read fails. The user accepted this gap as a limit.
- **Overdue reads come first.** The scheduler's timers also run on the
  monotonic clock, so after a wake the next scheduled settings read can be
  up to `overage_check_every` of awake time away. The scheduler records the
  wall time of each account's next read. Before routing a client request,
  the service reads, in parallel, every account whose scheduled read is more
  than 1 s overdue by wall time, and the request waits for those reads. A
  read of either kind resets the schedule, as soon as it starts. A request
  that arrives while another request's overdue read is in flight therefore
  does not wait for that read and decides on the account's current reading.
  Every request judges that reading by its wall-time age, and a stale
  reading sends the request through the on-demand reread, which waits for
  the read in flight and decides again. After a wake, the first request
  decides on readings taken after the wake unless a read fails. A failed
  read leaves the old reading, which is stale after a sleep longer than
  `overage_fresh_for`. No request dispatches on a reading that is stale by
  wall time (`TestAfterTheWallClockJumpsTheAccountIsReadBeforeDispatch`).

No offline test can put the machine to sleep. The tests move the injected
wall clock while no scheduler timer fires, which is what a sleep looks like
to the service. The live step W6 passed across 2,699 s of real sleep (row
WC-6). Both of its real attempts went out on settings reads 175 s old, under
the upstream gate's 25-minute wall-time guard
(`evidence/PR4/live-2-cc2.1.300/W6/upgate.jsonl`).

### Migration

A confirmed exhaustion before output is a 429 whose own attempt headers
reject a window that applies to the model (PR2, "Quota evidence must come
from the attempt"). `Report` records it, and the routing loop calls `Route`
again in the same client request. `Decide` returns `migrate` with reason
`exhausted` when another account is eligible, and `Route` journals the
migration before the service dispatches on the destination. The client
sees one response from the destination, and the request's
`upstream_attempts` counts both attempts. Only the bound account changes:
the request bytes, model, and session header are the client's, and the
destination receives the same session identity the source did
(`TestExhaustionBeforeOutputMovesTheConversationWithinTheRequest`).

- **Exclusion.** Placement skips every account with a rejection in force, so
  a destination that was already exhausted for this request is never
  chosen. If the destination's attempt is also rejected, the next step
  finds no eligible account and waits
  (`TestEveryAccountExhaustedWaitsForTheEarliestUsableReset`).
- **Attempt cap.** With `max_upstream_attempts` spent, the migration is
  still committed, and the client gets a local 429 with a reset 1 s away
  that names the destination. Its resend dispatches there
  (`TestMigrationWithTheAttemptCapSpentAsksTheClientToSendAgain`). The same
  answer goes to a concurrent request whose conversation another request
  moved after this one's last attempt
  (`TestWithTheAttemptCapSpentTheLoserOfAConcurrentMigrationIsAskedToSendAgain`),
  unless the policy fails that request first. For example, a request whose
  transient failures passed the policy's retry limit gets the policy's 503.
- **Concurrency.** Concurrent requests of one conversation commit one
  migration: `Commit` decides again under its lock, so a request that loses
  the race dispatches on the destination
  (`TestConcurrentExhaustedRequestsCommitOneMigration`). A request already
  dispatched keeps its pinned account, and a subagent request that follows
  the migration goes to the destination
  (`TestADispatchedRequestKeepsItsAccountWhileTheConversationMigrates`).
- **No return.** A migrated conversation stays on its destination when the
  source recovers (`TestMigratedConversationStaysAfterTheSourceRecovers`).
  It moves again only on a new confirmed exhaustion, observed paid use, a
  login requirement before it was served (PR2), removal of its account from
  `config.json`, or a manual move.
- **Cancellation.** A client that goes away during the destination's
  response cancels that attempt; the committed migration stays
  (`TestClientCancellationDuringTheMovedResponseKeepsTheMigration`).

### Waiting

When every account that could serve the model is blocked until a reset,
the router answers the local 429 of the client contract and makes no
upstream attempt. Its reset is the earliest usable reset over the
accounts: for each account, the latest reset among its rejections that
apply to the model. A near five-hour reset under a weekly rejection is not
usable.

When no account could serve even after a reset, the router refuses with
503 and `x-should-retry: false`, as PR3 does: no account is logged in, or
every account without a rejection in force is barred by paid overflow
enabled, paid use, or an unknown or stale check, and no account is blocked
until a reset. A conversation's own account is refused the same way when
it has no rejection in force and its check is enabled, or unknown or stale
after one reread.

The waiting is the client's: with
`CLAUDE_CODE_RETRY_WATCHDOG=1`, both clients sleep until the reset with no
connection open and send again, and cancel at once on SIGINT or
`interrupt()`. The router never holds a request until a reset. A request
waits in the router only for settings reads (overdue reads and rereads) and
for the backoff between upstream attempts. A client that goes away ends
the request, and a settings read it cancels counts as a failed read.

An account blocked until a reset counts toward the wait when its
paid-overflow check is unknown or stale. One with paid overflow enabled or
paid use does not. Without this rule, when every account is blocked and its
check has aged past `overage_fresh_for`, the router would refuse with
`no_included_only_account` (503, `x-should-retry: false`) and end the
client's wait. The check is read again before the account serves: at the
reset, the stale check refuses dispatch until a reread says `disabled`
(`TestAWaitThatOutlivesTheCheckReadsItAgainAtTheResetBeforeDispatch`). A
confirmed exhaustion with stale checks on both accounts waits for the
source's reset and asks for a reread, and the conversation migrates once the
destination's check is fresh
(`TestConfirmedExhaustionMigratesDespiteAStaleSourceCheck`).

When an unblocked account is held back only by an unknown or stale check,
`Decide` sets `RecheckOverage` on the `wait`. The service reads those
settings, once per account per request, and decides again before it
answers (`TestWaitRereadsAnAccountWhoseSettingsReadFailed`,
`TestAWaitRereadsAStaleAccountThatCouldServeBeforeTheReset`).

An unknown reset is answered without a reset header and with
`retry-after: 300`; the account is tried again `UnknownResetRecheck` after
the rejection (`TestUnknownResetWaitsWithoutPromisingATime`). `Validate`
refuses an `UnknownResetRecheck` above one week, because merging forgets a
reset rejection one weekly period after it was stamped (PR2 N20).

### Delivered output

The router never sends a request again after it has committed a response
(PR3, "Streams"). After a failure in the response it writes an SSE `error`
event, ends the stream, and keeps the assignment. The outcome is recorded
as `error_after_output` or `incomplete` on the `request` event
(`TestInterruptionAfterOutputIsReportedAndNeverResent`). An
exhaustion that shows only in a stream after output carries no attempt
headers, so it is not confirmed; the next request learns it from its own
attempt and migrates then.

Lane 2 observed the native clients, terminal Claude 2.1.285 and the Agent
SDK with T3's options, behind the router (`evidence/PR4/lane-2/recovery.json`):

- After a completed text block and the router's `error` event, both
  clients kept the block and sent one continuation request on their own,
  with no visible error. That request is a new turn of the conversation,
  not a resend of the cut one.
- After a completed `tool_use` and the `error` event, both clients showed
  that the response may be incomplete, ran the tool once, and continued
  with its result. A later turn did not run it again (sentinel count 1).
- After a `ping` and an SSE `overloaded_error`, both clients sent the
  request 3 more times without an `api_retry` event: twice streaming, 0.6 s
  and 1.2 s apart, then once non-streaming. That is the silent resend
  budget of the follow-up of the same name. Claude Code 2.1.300 and Agent
  SDK 0.3.300 do the same (`evidence/PR4/lane-2-cc2.1.300/recovery.json`).
  An error right after `message_start` gives a different count on 2.1.300
  (see "Routing loop").

Deviation from the plan, accepted: the plan says that partial output
"requires explicit retry". Neither native client waits for one: each sends
one continuation turn on its own after the cut. The router never resends the
cut request and no completed tool runs twice, but the router cannot make the
client wait for the user. On 2026-10-06 the user accepted "client-initiated
continuation, no router resend, no tool replay" as meeting the plan. The
live session cut no output, so this predicate rests on lane 2 alone.
Lane 2's records name one check of the cut scenarios
`explicit retry completed on the same account`. That check sends a further
user turn (`Continue.`) after the cut and passes when it completes on the
same account. It observes no retry of the cut request; the accepted
behavior is the client's own continuation turn.

### Login and manual movement

An `auth` failure marks the account as needing login. New conversations
skip it. A conversation that has been served on it gets 503 naming
`claude-router login -account ID`, never 401, and keeps its assignment. One
that never served moves (PR2). That move rests on a coordinator decision,
which the user has not accepted. The mark is cleared by:

- `claude-router login`, which clears it in the saved account state while
  it holds the state directory, so it applies at the next start;
- a settings read with the account's credential that began after the
  failed attempt and succeeded, which shows that the credential works
  (`login_confirmed` event). This covers a 401 that a refresh resolved.

`POST /claude-router/move` moves a conversation explicitly, whatever the
account's state (`TestRevokedLoginKeepsAssignmentsAcrossRestartUntilMovedOrConfirmed`,
`TestMoveRequiresTheClientTokenAndAnAssignedConversation`). Its answer and
its `migrated` event name the account the conversation left, read under the
commit lock, so concurrent moves report each transition once
(`Router.MoveFrom`, `TestManualOverrideMovesAndPersists`). `LoginConfirmed`
takes the commit lock before the router lock, in the same order as
`Relogin` and `Commit`. It waits for a commit in progress to finish, and a
commit that starts after it decides with the login requirement cleared.

### Durable account state

`router.Open` keeps each account's login requirement, known rejections,
latest paid-overflow check, and latest paid use in `accounts.json` beside
the journal. Every change is written before the call that made it returns:
a temporary file is synced and renamed, and the directory is synced. A
disabled check that only advanced by less than a minute, and a rejection
with a known reset that was observed again, are not rewritten; the saved
copy is older and therefore more conservative. A failed write stops the
store, like a failed journal write. The file holds no `disabled` check
that a backward clock step made stale (see "Wall time across sleep").

On load, a stamp later than the clock is clamped as live readings are:
blocking evidence is kept and stamped now, and a disabled check is
dropped. Utilization and allowed-window reports are not kept: the first
goes stale within `FreshFor`, and losing the second can only keep a
delayed rejection, which blocks longer. The record of an account left out
of the configuration is written back unchanged, so the account keeps its
rejections, login requirement, and paid use when it returns
(`TestAnAccountLeftOutOfTheConfigurationKeepsItsStateUntilItReturns`). As
long as `accounts.json` survives, a restart therefore never dispatches to a
known exhausted account before its reset; a deleted file starts with no
rejections
(`TestRestartDuringAWaitKeepsTheResetAndResumesAfterIt`,
`TestRestartBeforeTheResetNeverDispatchesToTheExhaustedAccount`,
`TestExhaustionLoginAndOverageStateSurviveRestart`). The simulator still
builds its router with `New`, so its restarts forget account state.

## Operation (PR5)

### Settings ownership

A settings file can have several owners, one per key. The installer refuses a
run in which two owners claim one key, and a run that would change the same
settings file for a harness and the component, which must run separately.
Router activation owns `apiKeyHelper`, `env.ANTHROPIC_BASE_URL`, and
`env.CLAUDE_CODE_RETRY_WATCHDOG` in the Claude settings file.
`claude_router.client_settings` returns their values: `apiKeyHelper` is `cat`
of the `client_token_file` path from `config.json`, resolved against the
directory of `config.json` as the service resolves it, and quoted for
`/bin/sh`, so relative paths and paths with spaces or quotes work
(`test_a_relative_token_path_is_read_from_the_state_directory`). Harness settings that name an owned key, or
`env.ANTHROPIC_AUTH_TOKEN` or `env.ANTHROPIC_API_KEY`, are refused, because
Claude Code uses either env token before `apiKeyHelper`. `client_settings`
refuses client settings that hold either env token, and returns the owned keys
whose existing values activation replaces, such as another `apiKeyHelper`.
The component's settings record is `settings.claude-router` in the manifest,
the format the harness targets use. PR5 writes none. Uninstall and `direct`
restore one if it exists, including a prior `apiKeyHelper`, byte for byte
(`test_a_prior_api_key_helper_is_restored_exactly_by_direct_and_by_uninstall`).

Claude Code 2.1.300 runs `apiKeyHelper` and sends its trimmed output as both
`X-Api-Key` and `Authorization: Bearer` (documented under "Authentication
precedence", and checked in a sandboxed client against a recorder and the
router, with a token path holding a space and a quote:
`evidence/PR5/apikeyhelper-r3/`). The router accepts either header.

N8 is closed only for stored copies of the client token: the settings file
activation writes, the manifest's `settings.claude-router` record, and
`direct` backups hold the helper command, not the token, so the token lives
only in `client-token`. The test scans those files, the manifest, every backup,
and every command output for the client token and for the fixtures' login
credential (`test_no_output_settings_file_manifest_or_backup_holds_the_client_token`).
These parts stay open:

- Claude Code uses `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY` before
  `apiKeyHelper` wherever it finds one. `client_settings` sees only the
  settings file it is given. Activation calls it, and warns about the other
  places Claude Code reads first, but it does not refuse on them and reads
  only the projects named with `--project` (Activation, below).
- The harness record format stores the settings file's original and last text,
  so any other secret a user keeps in that settings file is copied into the
  manifest and backups at mode 0600.

`apiKeyHelper` takes precedence over a credential stored by `/login`. In
Part C of PR6's live lane, Claude Code 2.1.302 had a working stored login in
its plaintext credentials file, and every request in both runs carried the
client token as both headers and completed through the router
(`evidence/PR6/lane-2/apikeyhelper-precedence.json`). At the cutover, the
terminal continuation that `activate` verified routed through the router
while the daily driver's keychain login was present
(`evidence/PR6/cutover/activate.json`).

### Supervision

`serve -supervised` keeps `supervision.json` beside its `-config` file, which
the installer puts in the state directory. Each start records its time before
the service reads its configuration; a clean stop on SIGINT or SIGTERM removes
it. An unreadable `supervision.json` is replaced by a new record. When 5
starts within 10 minutes have no clean stop, the next start records
`gave_up_at` and exits 0. A start that cannot save the record also exits 0
without serving. launchd (`KeepAlive` with `SuccessfulExit` false,
`ThrottleInterval` 10) and systemd (`Restart=on-failure`, `RestartSec=10`)
do not restart a job that exits 0. A failed start, including a configuration
that does not load, records its error
(`TestAConfigThatFailsToLoadCountsTowardTheLimit`,
`TestAnUnreadableSupervisionRecordStillBoundsRestarts`,
`TestASupervisedStartThatCannotRecordItselfExitsCleanlyWithoutServing`).
`serve -supervised` without `-config`, or with a relative one, exits 1 and
records nothing
(`TestASupervisedStartNeedsAnAbsoluteConfigAndCountsNothingWithout`).
Each save writes a temporary file with a unique name in the same directory and
renames it over `supervision.json`. Concurrent saves, such as `start`'s and a
respawned service's, do not fail on each other, and a temporary file left with
the wrong mode or owner does not stop a start
(`TestConcurrentSupervisionSavesEachSucceed`,
`TestALeftoverUnwritableTemporaryRecordDoesNotStopASupervisedStart`). A crash
between the write and the rename can leave a `supervision.json.<random>.tmp`
file, which nothing reads.
`claude-router start` clears the record, so an explicit start always runs.
`serve` without `-supervised` says that nothing restarts it.

## Activation (PR6)

PR6 points Claude Code at the router only after an acceptance record matches
the installation. Activation and its undo live in `scripts/claude_router.py`.
PR6 adds one service field, `binary_sha256` in `GET /claude-router/status`,
the SHA-256 of the executable file that `serve` hashes as its first step,
before it reads its configuration or starts the SDK
(`TestStatusReportsTheExecutableDigestTakenAtStart`,
`TestExecutableDigestIsTheSHA256OfTheRunningExecutable`). Activation needs it
to compare the running binary, not only the file on disk, which an update
replaces while the old binary keeps running.
The service also reports `code_sha256`, the router code digest that the
installer passes to the linker, or `unknown` for a build without it
(`TestStatusReportsTheCodeDigestTheInstallerStamped`).

### Acceptance record

`claude_router.py identity --claude PATH --agent-sdk DIR` prints the
installation's identity as JSON: `head`, `code_sha256`, `binary_sha256`,
`helpers_sha256`, the running binary's `running_binary`,
`running_code_sha256`, and `running_binary_sha256`, `sdk`, `go`, `platform`
(`<os>/<arch>`), and `clients`. `claude_router.py identity --code-only` prints
only `code_sha256` and `helpers_sha256`, computed from the checkout without
an installation or client paths. The acceptance run saves the identity with
its verdict. Activation and `check` read these fields of the record:

| Field | Activation compares it with |
| --- | --- |
| `result` | Must be `pass`. |
| `code_sha256` | Must be 64 hex digits and equal the installed `code_sha256` in the astack manifest and the running service's `code_sha256`. The digest uses the line format of `helpers_sha256` over the router code (Installation, above), with paths relative to `components/claude-router/` (`test_the_code_digest_covers_tracked_router_code_and_skips_docs_tests_testdata_and_the_record`). |
| `helpers_sha256` | Must be 64 hex digits and equal the digest of the installed helper payload in `lib/`. For each file in `lib/`, sorted by relative path, the digest input holds one line: the relative path, a NUL byte, and the file's SHA-256 in hex. `__pycache__` and compiled files are skipped. The digest is the SHA-256 of these lines (`test_the_helpers_digest_covers_each_installed_file_by_path_and_content`). See "Which code runs" below. |
| `sdk` | The running service's `sdk`, the pinned CLIProxyAPI module version. |

Activation also requires that the running service's `binary_sha256` equal
the SHA-256 of the installed `bin/claude-router`, so a service that still
runs the binary an update replaced refuses. `head`, `binary_sha256`, `go`,
`platform`, and `clients` are information only. A record therefore matches
at another commit with the same router code, another build of it, and other
client versions (`test_a_record_matches_by_code_digest_at_another_commit`,
`test_a_record_with_another_head_build_and_client_versions_activates_when_check_passes`).
When the record's `platform` differs from this host's, activation prints
`note    accepted on <record platform>, this is <host platform>`, followed
by `, not yet tested on real Linux` on Linux, and continues
(`test_activation_on_another_platform_than_the_record_s_names_both`).

A missing record, a record that does not parse, or any mismatch refuses
before any write and lists every mismatch
(`test_a_missing_or_mismatched_acceptance_record_refuses_before_any_write`).
The installer copies the helpers from the working tree, so an edit under
`scripts/` changes `helpers_sha256`
(`test_an_install_from_an_edited_checkout_refuses_before_any_write`), and it
refuses to build router code that differs from the commit.

`components/claude-router/accepted.json` holds the record of the live
acceptance run at the router code it names. A change to the router code
needs a new acceptance run and record.

### Check

`claude_router.py check [--home DIR | --manifest FILE] [--claude PATH]
[--settings FILE] [--acceptance FILE] [--timeout 120]` prints one line per
check, with a 9-column label of `ok`, `fail`, or `skip`. `--home` and
`--manifest` exclude each other, and `activate` takes them the same way
(`test_home_and_manifest_together_are_refused`):

1. The router answers `GET /claude-router/status` at the configured
   `listen`, named with the manager.
2. Every account in `config.json` is registered and needs no login.
3. Every account's paid-overflow reading is `disabled`. `enabled` or
   `paid_use` fails with `paid overflow on for NAME` and `next      turn off
   NAME paid overflow on claude.ai; claude-router check`. A missing reading
   fails with `paid overflow not read yet for NAME`.
4. The settings file holds the three keys of `client_settings` with the
   router's values. The default file is the one `activation.json` names,
   then `$CLAUDE_CONFIG_DIR/settings.json` or `~/.claude/settings.json`.
5. The acceptance record, by default the installed `accepted.json`, matches
   (Acceptance record, above). The line names the record's `platform`, and
   each mismatch follows on its own line.
6. When every line before passed, `check` runs `claude -p ping --session-id
   <new UUID> --strict-mcp-config --no-session-persistence --tools ""` with
   `/bin/sh -c` in its own process group, stdin from `/dev/null` and its
   output discarded, for up to 120 seconds. The line passes when
   `events.jsonl`, from its size before the run, holds a `request` event
   whose `conversation` is that session's hash, with status 200 and outcome
   `completed`. Other requests, including the client's side requests and
   failed requests of the same session, do not count
   (`test_check_passes_every_line_and_finds_its_own_request_among_side_requests`,
   `test_check_fails_when_only_another_session_is_answered`). The line
   names the account of the last such request and the client's run time.
   Otherwise the line is `skip      test message, not sent while a check
   fails`, and no message is sent
   (`test_check_fails_and_sends_no_message_while_paid_overflow_is_on`).

When the router does not answer, `check` still prints every line of the
layout. Lines 2, 3, and 5 print `skip` with `accounts, not read while the
router is stopped`, `paid overflow, not read while the router is stopped`, and
`accepted record, not compared while the router is stopped`
(`test_with_the_router_stopped_check_prints_every_line_and_skips_what_it_cannot_read`).
With no accounts in `config.json`, line 3 is `skip      paid overflow, no
accounts to read`.

`check` installs the signal handlers of activation's verification. SIGINT,
SIGTERM, or SIGHUP kills the test message's process group, prints
`check     interrupted`, and exits 1
(`test_a_signal_ends_the_test_message_client_with_check`).

The last line is `check     passed` or `check     failed`; a brief
activation leaves out `check     passed`. A failure adds
`next      <step>` for the first failed check and exits 1. `check` never
prints the prompt or the reply. The layout is the user's pick, check A
(`cmd/claude-router/testdata/check/`), and every line fits 80 columns for
three accounts of 8 characters
(`test_lines_fit_eighty_columns_with_three_eight_character_accounts`).

### Which code runs

The helper payload is `claude_router.py`, `astack_files.py`,
`astack_settings.py`, and `_vendor/`. The Go `claude-router direct` runs the
installed copy in `lib/`. `activate` and `./uninstall.sh` run the copy in the
checkout they are started from. Before anything else, `activate` computes the
same digest over the payload it is running and refuses when it differs from
the installed `lib/`, or when `lib/` is missing:

```text
claude-router: activate: the helpers running this command differ from the installed ones
        helpers: running <12 hex> from <scripts directory>, installed <12 hex or none>
next    run ~/.local/share/astack/claude-router/lib/claude_router.py instead
```

When the refused command already runs from `lib/`, or `lib/` is missing, the
last line is `next    reinstall from a checkout of the accepted head:
./install.sh --component claude-router`.

Uninstall applies the same check when the manifest records the component and
uninstall would restore client settings, that is, when
`settings.claude-router` owns a file or `activation.json` exists. It exits 1
with `Uninstall would restore client settings, but the helpers running this
command differ from the installed ones (...); run claude-router direct, then
uninstall`
(`test_activation_refuses_when_the_running_helpers_differ_from_the_installed_ones`,
`test_an_edited_checkout_refuses_before_it_undoes_an_interrupted_activation`,
`test_uninstall_refuses_to_restore_settings_with_helpers_other_than_the_installed_ones`).

So `activate`, and an uninstall that restores client settings while the
component is installed, run only helper bytes equal to the installed `lib/`.
These paths run without that check:

- The Go `claude-router direct` runs `lib/` itself and does not compare it
  with the record's `helpers_sha256`. An edit to `lib/` after activation runs.
- `claude_router.py direct`, the internal subcommand the Go `direct` calls,
  runs unchecked when started by hand from a checkout.
- An uninstall from a checkout when the manifest keeps
  `settings.claude-router` but has no `components.claude-router` record. The
  tools never write that state.
- `scripts/manage.py`, the entry point of `./install.sh` and
  `./uninstall.sh`, which calls the payload.
- `service.json`, from which the Go `direct` reads the helper path and the
  Python interpreter.

### Order of operations

`claude_router.py activate [--acceptance FILE] [--claude PATH] [--verify
SESSION COMMAND]... [--settings FILE] [--project DIR]... [--prepare]
[--brief] [--home DIR | --manifest FILE] [--lock-fd FD]` runs these steps.
`--acceptance` defaults to the installed `accepted.json`. `--claude`
defaults to `claude` on `PATH` and runs the check's test message.
`--settings` defaults to `$CLAUDE_CONFIG_DIR/settings.json`, or
`~/.claude/settings.json` without it or with `--home`. `--brief`, which
`setup` passes, prints the `note` and `warn` lines, the check lines without
`check     passed`, and `activated Claude Code routes through the router`
in place of the other lines.

`activate` and `direct`, in every mode, hold an exclusive `flock` on
`activation.lock` in the state directory for the whole run, including
verification. Every install and uninstall over an installed router holds it
too, except with `--dry-run`, with or without `--component` (Update, under
Installation), and so do `setup`, `account add`, and `account remove`
(Commands, under Operation). With `--lock-fd`, `activate` and `direct` lock
the descriptor their caller passes, which already holds the lock. A second
caller refuses before it reads `activation.json` or changes anything.
`activate`, install, and uninstall read the manifest once before the lock, to
find the state directory, and read it again under the lock. `direct` reads it
only under the lock. The refusal prints `claude-router: <command>: another
claude-router setup, account, activate, direct, install, or uninstall is
running` and `next    wait for it to finish, then run again`, and exits 1.
Install and uninstall print `astack:` and the same two parts on one line.
`claude-router direct` takes the lock before its check, holds it through the
service stop and the apply, and passes it to the helper as an open descriptor.
With no state directory, the helper's `activate` and `direct` print
`no state directory at <dir>` and exit 1. The Go `claude-router
direct` finds no `service.json` there and prints `claude-router: direct: no
astack installation records this state directory; direct recovery needs one`,
exits 1, and creates nothing. Uninstall with the lock held refuses before it
stops the service or removes a file, whether or not `activation.json` exists.
When uninstall finds the state directory but cannot open `activation.lock` in
it, it prints `astack: no state directory at <dir>` with no next step
(`test_an_activation_during_another_s_verification_refuses_without_changes`,
`test_direct_during_an_activation_s_verification_refuses_without_changes`,
`test_a_second_activation_whose_verification_fails_refuses_before_it_touches_the_first`,
`test_uninstall_during_an_activation_s_verification_refuses_without_changes`,
`test_direct_runs_under_the_lock_its_caller_holds_and_hands_down`,
`test_uninstall_while_the_lock_is_held_before_any_activation_record_removes_nothing`,
`test_uninstall_that_cannot_open_the_lock_names_no_next_step`,
`test_direct_with_a_missing_state_directory_refuses`,
`TestDirectWithAMissingStateDirectorySaysNoInstallationRecordsIt`,
`TestDirectRefusesWhileAnotherActivateOrDirectHoldsTheLock`,
`TestDirectHoldsTheLockAcrossTheCheckTheStopAndTheApplyAndHandsItToTheHelper`).

1. Check that the running helpers are the installed ones (Which code runs,
   above). Then undo an interrupted activation (below). With `--prepare`,
   run only the undo's checks. A refusal exits 1, as `direct -prepare` does.
   Otherwise print `undo    an interrupted activation of <file>; activate
   restores it first` and `ready   nothing changed; activate without
   --prepare`, and exit 0 before step 2. Without `--prepare`, the undo
   prints `undo    <file> restored after an interrupted activation`. When
   the file already holds the original SHA-256, both modes print
   `skip    <file> (already the original; interrupted activation)` in place
   of the `undo` line, as `direct` does
   (`test_the_next_activation_undoes_an_interrupted_verification_first`,
   `test_the_next_activation_says_it_skips_a_settings_file_the_interruption_left_unchanged`).
2. Refuse when `settings.claude-router` already owns a file: `claude-router
   direct` comes first.
3. Read the record, ask the running service for its status with the client
   token, and compare (Acceptance record, above). A service that does not
   answer refuses with `next    claude-router start, then run again`.
4. Check readiness: the assignment journal is `ok`, and at least one account
   is registered, needs no login, and has a `disabled` paid-overflow reading
   (`test_a_router_that_is_not_ready_refuses_before_any_write`).
5. Call `client_settings` on the settings file. An env token in that file
   refuses. Each owned key prints `set`, or `replace` when it already holds
   another value. A replaced `env.ANTHROPIC_BASE_URL` prints the old and new
   values. A replaced secret-named key, such as a foreign `apiKeyHelper`,
   prints only `the old value stays in <backup>`, because a helper command
   can hold a secret.
6. Print a `warn` line, without values, for each other place Claude Code
   reads first: a `--project` directory's `.claude/settings.json` or
   `.claude/settings.local.json`, or the managed settings file
   (`/Library/Application Support/ClaudeCode/managed-settings.json`,
   `/etc/claude-code/managed-settings.json`), that sets an owned key or an
   env token; and `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY` in the
   environment of the command or in `launchctl getenv` or `systemctl --user
   show-environment`
   (`test_local_settings_and_environment_tokens_are_refused_or_named`).
   Activation checks no other project.
7. With `--prepare`, stop here.
8. Copy the settings file to
   `backups/activate-<first 12 hex of its SHA-256>/settings.json` with mode
   0600, and write `activation.json` in the state directory with phase
   `writing`: the settings path, its mode, the original and activated
   SHA-256, the backup path, the accepted identity, and the undo command
   `claude-router direct`.
9. Write the settings and their `settings.claude-router` record, as the
   harness targets do, then set the phase to `verifying`.
10. Run each `--verify` `COMMAND` with `/bin/sh -c` in its own process group.
    Each must exit 0 within `--verify-timeout` seconds (default 600) and add
    at least one `request` event to `events.jsonl` whose `conversation` is
    the first 12 hex digits of the SHA-256 of its `SESSION`, the Claude
    session ID the command continues, with status 200 and outcome
    `completed`. A request for another conversation does not count, even
    when it arrives while the command runs
    (`test_a_continuation_counts_only_requests_of_its_own_conversation`). A
    client that sends the wrong token gets the router's 401 and fails this
    check. Output names a command by its program, the first word that is
    not a `NAME=value` assignment, and never prints its arguments:
    `verify  <program> (conversation <hash>): exit 0, <n> routed request[s]`.
11. When each command ends, by exit, by timeout, or by a signal to
    activation, activation sends SIGKILL to the command's process group
    (`test_a_continuation_s_children_are_killed_when_it_ends`,
    `test_a_timed_out_continuation_is_killed_with_its_children`). A process
    that starts its own session or process group, such as a Node child
    spawned with `detached: true`, is not in that group and keeps running.
12. Step 10 fails on any of these:
    - a nonzero exit, even after a counted request
    - a timeout
    - no counted request
    - SIGINT, SIGTERM, or SIGHUP to activation, including the SIGHUP from
      closing the terminal, from the start of step 8 until the last signal
      check (below)

    From the start of step 8 until activation exits, these signals do not
    stop activation. The first one blocks all three until activation exits
    and sends SIGKILL to the running command's process group. Activation
    kills any command it starts after that. It checks for a signal before
    and after each command and once more after the last one. When a check
    finds one, the failure line is `claude-router: activate: verification
    was interrupted`. A signal after that last check changes nothing.
    A signal that was ignored when activation started stays ignored: under
    `nohup`, a hangup does not stop the verification. Before step 8 the
    signals have their usual effect. SIGQUIT (Ctrl-\\) is not handled: it
    ends activation with the settings on the router and `activation.json`
    in phase `verifying`, and the running command keeps running.
    `claude-router direct` or the next `activate` restores the settings.

    On a failure, activation prints the failure and undoes the write as an
    interrupted activation does (below). It then prints `undo    <file>
    restored; the router keeps its logins and assignments` and `next
    claude-router status`, and exits 1. Signals during the undo change
    neither the undo nor the exit status. When a line cannot be written to
    stdout or stderr, because the terminal or a pipe's reader is gone,
    activation sends the rest of that stream to `/dev/null` and keeps
    writing the other stream, and the undo and the exit status stay the
    same
    (`test_a_failed_or_unrouted_continuation_restores_the_direct_settings`,
    `test_an_interrupted_verification_restores_the_direct_settings`,
    `test_repeated_and_mixed_signals_do_not_stop_the_undo_or_change_the_exit_status`,
    `test_signals_from_many_parallel_senders_do_not_stop_the_undo_or_change_the_exit_status`,
    `test_a_signal_while_activation_exits_changes_neither_the_result_nor_the_exit_status`,
    `test_signals_during_the_undo_after_a_failed_continuation_do_not_stop_it`,
    `test_signals_ignored_when_activation_starts_stay_ignored`,
    `test_closing_the_terminal_during_verification_restores_the_direct_settings`,
    `test_a_stdout_that_breaks_during_verification_keeps_the_failure_lines_on_stderr`,
    `test_a_stdout_without_a_reader_changes_neither_stderr_nor_the_exit_status`).
13. If the settings file changed while the command ran, that undo refuses.
    Activation prints `<file> changed after an interrupted activation` on
    stderr, also when stdout is gone
    (`test_a_stdout_that_breaks_during_verification_keeps_the_edit_refusal_on_stderr`),
    leaves the file with the router's keys and the edit, leaves
    `activation.json` in phase `verifying`, and exits 1. `claude-router
    direct` and the next `activate` refuse the same way for as long as the
    file holds neither the activated nor the original bytes and
    `activation.json` exists. Removing only the router's keys does not end
    this. The printed `next` line names the recovery: restore the file, or
    remove the router's keys by hand, then delete `activation.json`; after
    that `claude-router direct` drops the record and keeps the edit
    (`test_a_settings_edit_during_a_failed_continuation_is_kept`).
14. The router never sends a request around itself: a stopped router fails
    the client's request (`evidence/PR6/lane-3/cutover-isolated.json`, step
    `unavailable_after_activation_no_bypass`).
15. After the last `--verify` command, run `check` (Check, above) on the
    settings file just written, with the record read in step 3. A failed
    check prints the check lines, undoes the write, prints `undo    <file>
    restored; the router keeps its logins and assignments` and `next
    claude-router status` on stderr, and exits 1
    (`test_a_failed_check_restores_the_direct_settings`). A `--verify`
    command or a check that raises an `OSError`, `ValueError`, or `KeyError`,
    such as an unreadable `events.jsonl`, prints `claude-router: activate: the
    check could not finish: <error>` and undoes the write the same way
    (`test_a_check_that_cannot_read_the_events_restores_the_direct_settings`).
    The check runs inside the signal handling of step 12.
16. Otherwise set the phase to `active`, print `done    clients connect
    through the router; undo with claude-router direct`, and exit 0.

Activation never starts, stops, or enables the service, and never touches
logins, assignments, or the client token. `--verify` is optional, and
activation does not know which client a command runs. The runbook's cutover passes two, a
terminal continuation and an Agent SDK continuation with T3's options
(`reports/PR6-live-runbook.md`, Part E), and then checks a T3 message
through the router. The spec's check of one terminal and one T3
continuation is therefore a runbook step; activation does not enforce it.

### Undo and interrupted activation

`claude-router direct` is the rollback. It stops the router as `stop` does
and restores the owned keys from the `settings.claude-router` record, as in
PR5, and then removes `activation.json`. Logins, assignments, the client token,
the binary, and the job stay (`evidence/PR6/direct-recovery.json`). With no
owned record and no `activation.json`, `direct` changes no settings, and
`claude-router direct` leaves the service running.

An `activation.json` in phase `writing` or `verifying` marks an activation
that did not finish. `direct`, and the next `activate`, undo it by file
hashes. `direct` also undoes an `active` one by file hashes when the
manifest holds no `settings.claude-router` record, as after a concurrent
install drops the record (Known limits, below):

| Settings file | Action |
| --- | --- |
| Holds the activated SHA-256 | Restore the backup with the recorded mode, after checking the backup's SHA-256, or delete the file when it did not exist before. A changed backup refuses. |
| Holds the original SHA-256 | Nothing to restore. |
| Anything else | Refuse, name the backup, and keep the edit. |

Both then drop the file's `settings.claude-router` record and
`activation.json`. `direct --check` and `direct -prepare` apply the same
checks without writing. When the undo would refuse, `direct --check` exits 1
with the refusal, so `claude-router direct` refuses before it stops the
service; otherwise `claude-router direct` stops the service first.
`direct -prepare` prints `restore <file> (interrupted activation)`, or
`restore <file> (activation with no settings record)` for an `active`
journal. When the file holds the original SHA-256, it prints `skip    <file>
(already the original; <reason>)` in place of the `restore` line. For an
`active` journal the refusal reads `<file> changed after activation`, and
`activation.json` stays in phase `active`
(`test_direct_without_a_settings_record_restores_the_activation_backup`,
`test_direct_without_a_settings_record_refuses_an_edited_file_and_keeps_the_activation_record`,
`test_direct_without_a_settings_record_says_it_restores_nothing_when_the_file_is_already_the_original`).
Uninstall refuses while a `writing` or `verifying` journal exists, or an
`active` one without a `settings.claude-router` record, and keeps the
journal, because the helper that undoes it is part of the payload uninstall
removes. Its message ends `run claude-router direct, then uninstall`
(`test_uninstall_without_a_settings_record_refuses_and_keeps_the_activation_until_direct`,
`test_direct_and_uninstall_after_an_interruption_between_the_settings_write_and_its_record`,
`test_direct_after_an_interruption_before_the_settings_write_drops_the_record`,

### Legacy account switcher

The spec retires the legacy account switcher (`claude-accts`) only where it
shares credentials or client configuration with the router. Nobody has
inspected the switcher, because a standing order forbids reading it or
`~/.claude-accounts`, so whether the two share anything is unverified.

The router reads and writes these files and keys, and no others that its
code names:

- Its own files. These are the payload in
  `$XDG_DATA_HOME/astack/claude-router/`, the launchd or systemd descriptor
  and the label's login switch (Installation, above), and the state
  directory `$XDG_STATE_HOME/astack/claude-router/`. The state directory
  includes `config.json`, `client-token`, `service.json`,
  `supervision.json`, `accounts.json`, `events.jsonl`, `assignments/`,
  `activation.json`, `activation.lock`, and `auths/`.
- Its own credentials. These are the logins in `auths/<account>.json`,
  which `claude-router login` writes from its own OAuth sign-in. The service
  points the SDK's `auth-dir` at `auths/`. Neither the Go code nor the
  helper names `~/.claude.json` or Claude Code's stored login, which Claude
  Code keeps in the macOS keychain or in `.credentials.json`.
- Its records in the astack manifest, `components.claude-router` and
  `settings.claude-router`, and the backups under
  `$XDG_STATE_HOME/astack/backups/`.
- Three keys in the Claude settings file that `activate` targets:
  `apiKeyHelper`, `env.ANTHROPIC_BASE_URL`, and
  `env.CLAUDE_CODE_RETRY_WATCHDOG`. `activate` writes them, and `direct`
  and uninstall restore them. `activate` also reads
  `env.ANTHROPIC_AUTH_TOKEN` and `env.ANTHROPIC_API_KEY` in that file.

Without writing, `activate` reads the owned keys and the two env tokens in
each `--project` settings file and in the managed settings file.
It reads the two env tokens in its own environment and in the output of
`launchctl getenv` or `systemctl --user show-environment`. It runs `--claude
PATH --version` and reads `--agent-sdk DIR/package.json`.

Of these, the Claude settings file is the one that tools outside astack
also write, and the router owns only its three keys there. If the switcher
writes one of them, activation prints `replace` for it, and `direct` refuses
on a key edited after activation and keeps the edit. While activated, Claude
Code sends the client token from `apiKeyHelper` instead of its stored login
(Settings ownership, above), so a change to the stored login does not change
the account that serves a routed request.

The most plausible interference touches none of these files. `activate`
wires the settings file it resolves when it runs (Order of operations,
above). Claude Code reads `settings.json` in the `CLAUDE_CONFIG_DIR` of its
own process, or in `~/.claude` when that variable is unset. If the switcher
sets `CLAUDE_CONFIG_DIR` per account, Claude Code reads a settings file that
`activate` did not wire, uses the login stored for that directory, and
bypasses the router. Activation does not read `CLAUDE_CONFIG_DIR` from
`launchctl getenv` or `systemctl --user show-environment`, and each
`--verify` command runs in activation's own environment, so neither check
notices such a client.

The missing control is an inspection of the switcher: whether it writes an
owned key, an env token, or the router's files, and whether it sets
`CLAUDE_CONFIG_DIR`. The standing order does not allow that inspection here,
so the retirement requirement stays blocked (Verification, below).

### Known limits

- A client update after activation is not checked. Claude Code and T3 update
  themselves, and the acceptance record then names an older client.
- During `login`, `setup`, and `account add` with `-no-browser`, or when the
  browser does not open, the SDK prints SSH tunnel instructions and looks
  up this machine's public IP address over the network to fill them in. The
  router hides the instructions but cannot stop the lookup.
- `--agent-sdk DIR` is the caller's choice. Activation compares the version
  in its `package.json` with the record and does not check that it is T3's
  bundled SDK. The runbook's `t3-check` step compares the SDK version that
  T3's app bundle carries with the record.
- `--verify` counts requests by conversation, not by process. A request in
  the named session from another client, or one that started before the
  command and completed while it ran, also counts. Name a session that
  nothing else uses, as the runbook's cutover does.
- A passing `--verify` says nothing about clients and environments its
  commands do not run. A project not named with `--project`, or an app
  started with an env token, can still bypass the router's wiring;
  activation only warns.
- An install takes no lock. A concurrent `./install.sh` during activation
  can lose the settings record. `direct` then undoes the activation from
  `activation.json` and the backup, and uninstall refuses until it has (Undo
  and interrupted activation, above).

## Cache cost of account moves (PR7)

`claude-router cache` reports how much of the cache writes in a window come
from conversations that changed accounts. It reads only `events.jsonl` and
`config.json`, so it works while the router is stopped and with a missing or
malformed `service.json`. `claude-router status` warns when that share for
the last 24 hours exceeds `move_cache_warn_percent`. It computes the share
from `events.jsonl`, so the warning also shows while the router is stopped.

### Definitions

- **Move.** A `request` event with status 200 on an account other than the
  account of the same conversation's previous `request` event with status
  200, at any earlier point in the log. The move is that status-200 request
  itself. A request that fails on the new account first is not a move, and
  neither is a `request` event without an account, such as a wait. The
  digest reads the whole log to find the previous account and counts a move
  only when its own `at` falls in the window.
- **Placement.** The first status-200 request of a conversation. It is not a
  move, even after a `migrated` event with reason `never_served_relogin`.
- **Counted request.** A `request` event with an account, in the window,
  whose usage reports the input, cache write, and cache read counters, none of
  them `null`. Every sum below uses counted requests only. The move cost and
  all cache writes therefore come from the same requests, and the move share
  cannot exceed 100%.
- **Move cost.** The `cache_creation_input_tokens` of the move's own request,
  when that request is a counted request. Later requests, and cold starts
  after the cache expires, do not count.
- **Unknown cost.** A move whose request is not a counted request has an
  unknown cost. Its request reported no usage, or a `null` input, cache
  write, or cache read counter. A later request on the new account does not
  set the cost.
- **Reason.** The reason of the conversation's latest `migrated` event since
  its previous status-200 request, for example `exhausted` or `manual`. A move
  without one takes the `reason` of its own `request` event.
- **Unknown request.** A `request` event with an account, in the window, that
  is not a counted request. It adds nothing to the sums, and `cache` shows the
  account's count as `+ N unknown`. A failed request without usage is not an
  unknown request. It counts nowhere and adds no account line.
- **Hit rate.** read / (input + write + read) over the account's counted
  requests, rounded down. With no counted request, or counted requests that
  sum to 0 tokens, the hit rate is `--`. The lifetime `cache` rate in
  `status` uses the same formula over a different set: every `request` event
  in the log with a conversation, an account, and usage, with a `null`
  counter read as 0.
- **All cache writes.** The sum of the cache writes of the counted requests
  on every account.
- **Move share.** The sum of the known move costs divided by all cache writes.

`status` keeps its per-account `cache` rate over the whole log. Only the move
share in `status` and every number in `cache` use the window.

### Output

The layouts are the operator's picks: mock `cache A`, the `cache unknown`
moves line, and mock `status warning A`. `cmd/claude-router/testdata/cache/`
holds the `cache` screens, and `TestCacheMatchesTheSelectedLayout` renders
them and checks that each line fits in 80 columns.

```text
window    last 24h, 23:05 PDT yesterday to now
work      hit 95%  input 18k  write 2.10M  read 41.30M
alumni    hit 94%  input 18k  write 2.32M  read 41.25M  + 1 unknown
personal  hit 95%  input 18k  write 2.00M  read 41.25M
moves     5  cost 412k + 1 unknown  of 6.41M writes  share 6.4% or more
reasons   exhausted 3, manual 2
```

- `cache` lists the accounts in `config.json` in order, then any other
  account with a counted or unknown request in the window.
- `+ N unknown` on an account line counts its unknown requests. On the
  `moves` line it counts the moves with an unknown cost, and the share then
  ends in `or more`. The share counts known move costs only.
- With no cache write in the window, the share is `--`. The `reasons` line
  appears only when there is a move.
- `-since` takes a Go duration, default `24h`, and must be positive.

`status` shows the warning line when all of these hold:

- `config.json` loads.
- `move_cache_warn_percent` is above 0.
- All cache writes in the last 24 hours are above 0.
- The move share exceeds the setting. A share equal to the setting does not
  warn.

When a move in the last 24 hours has an unknown cost, the share in the line
ends in `or more`, as in `cache`. On a running router the line follows the
recent moves, as the last problem line. On a stopped router it follows the
`router  stopped` line and any `last error:` line. Three screens do not show
it: a configuration error, a start that status cannot record, and
`router  failed`. `status -v` does not show it either.

```text
cache   account moves wrote 14.0% of all cache writes in 24h, over 10%
next    claude-router cache
```

```text
router  stopped  127.0.0.1:18787  launchd                            14:20 PDT
cache   account moves wrote 14.0% of all cache writes in 24h, over 10%
next    claude-router start
```

The `next` line names `claude-router cache` only when no other next step
applies. On a stopped router the next step stays `claude-router start`.

### Setting

| Field | Contract |
| --- | --- |
| `move_cache_warn_percent` | An integer from 0 to 100. Absent or `null` means 10. 0 turns the warning off. For an integer outside 0 to 100, `status` shows `config error: move_cache_warn_percent: <value> is outside 0 to 100`, and `serve` refuses to start with the same error. A value that is not an integer does not decode. For `1.5`, `status` shows `config error: <config.json path>: json: cannot unmarshal number 1.5 into Go struct field Config.move_cache_warn_percent of type int`, and `serve` refuses with the same error. `cache` ignores the value, even outside 0 to 100, but it decodes `config.json`, so for a value that is not an integer it exits 1 with the same decode error. |
