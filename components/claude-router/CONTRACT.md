# Claude router integration contract

This file records what PR1 established about the pinned CLIProxyAPI SDK, the
storage design, and distribution. It is the input to PR2 through PR6. The
behavior contract is [the routing spec](../../docs/specs/claude-account-routing.md).
Rows that depend on terminal Claude, the Claude Agent SDK used by T3 Code, or a
live subscription stay `pending client evidence` until the client lanes report.

Evidence paths that begin with `evidence/` resolve from the execution store
(`CLAUDE_ROUTER_STORE`). Every SDK transcript is regenerated by the named test in
`probes/`. The [README](README.md) shows how to run the probes.

## How the router drives the SDK

These are the integration facts PR3 builds on. Each one is exercised by the
probes or read from the pinned source.

- The stock `POST /v1/messages` handler cannot be pinned. `ClaudeCodeAPIHandler`
  builds its execution context from `context.Background()`
  (`sdk/api/handlers/claude/code_handlers.go:238`), so a middleware value on
  the request context never reaches `requestExecutionMetadata`. The router
  registers its own route with `api.WithRouterConfigurator`, then calls
  `BaseAPIHandler.ExecuteStreamWithAuthManager` with a context carrying
  `handlers.WithPinnedAuthID` and `handlers.WithSelectedAuthIDCallback`.
- The selected-auth callback is the only per-request proof of the account the
  SDK used. A pin to an unknown or cooling-down auth returns HTTP 503 with no
  callback and no upstream attempt. An upstream 503 returns the same status with
  one callback. The router tells them apart by the callback.
- `cliproxy.Builder.Build` replaces the core manager's round tripper provider.
  The probe sets its provider after `Build` and before `Run`.
- The SDK's Claude OAuth refresh and profile clients dial `platform.claude.com`
  and `api.anthropic.com` with their own uTLS transport. They ignore the
  manager's round tripper (`internal/auth/claude/anthropic_auth.go:189`).
- Account files in the SDK auth directory carry no `base_url`, so inference
  always targets `https://api.anthropic.com`. The probe serves that host in
  process through the round tripper and refuses every other host. No probe
  request left the process. Every transcript records an empty `refused_hosts`
  list.

## Executor posture

The router runs the SDK as a single-attempt pinned executor and owns every retry
and migration decision.

| Setting | Value | Reason |
| --- | --- | --- |
| `routing.retry.request-retry` | `0` | With cooling disabled, SDK retry rounds retry the pinned account immediately, with no backoff. |
| `requests.streaming.bootstrap-retries` | `0` | Bootstrap retries also stay pinned, but hide pre-output failures from the router. |
| `routing.cooldown.disable-cooling` | `true` | With cooling on, one 503 blocks the pinned account. Later pinned calls fail without an upstream attempt. |
| `routing.session-affinity` | `false` | Stock affinity is in memory, model-keyed, and fails over when the bound auth is unavailable. |
| `routing.strategy` | any | A pin overrides every strategy tested. |
| `requests.passthrough-headers` | `false` | Error values carry no upstream headers whatever this setting says, because the Claude executor's `statusErr` has no `Headers()` method. |

The SDK configuration is written once before `Service.Run` and never edited while
the service runs. To change it, restart the service. The [data race
section](#sdk-data-races) explains why.

## Failure classification

The router classifies a failure before output from three SDK sources, as
implemented in `probes/classify.go`.

- The status code on the error the handler returns.
- `IsCredentialScoped()` on that error. The SDK sets it when a shared
  five-hour or weekly window reports `rejected`.
- The pinned account's passive header snapshot, `ModelStates[model].Quota.Signals`,
  read right after the failure. It holds the `Anthropic-Ratelimit-Unified-*`
  headers and `Retry-After` from the failed response.

| Class | Signal | Router action (spec) |
| --- | --- | --- |
| `transient` | 408 or 5xx, including 529 | Bounded retry on the assigned account |
| `throttle` | 429, not credential-scoped, no unified rejection in the snapshot | Bounded retry on the assigned account |
| `exhausted` | 429, credential-scoped or a rejected 5h or 7d window in the snapshot | Record exhaustion, migrate |
| `model_limit` | 429, unified rejection with only overage or model-specific claims | Pending: no live header capture yet |
| `auth` | 401 or 403 | Exclude from new placement, keep assignments |

These signals are unavailable or unreliable:

- Error values carry no response headers. `statusErr` has no `Headers()` method,
  so `ErrorMessage.Addon` is empty.
- `RetryAfter()` adds a random 1 to 30 second grace to every reset. Read exact
  reset times from the snapshot.
- The snapshot is one per account. Any later response on that account replaces
  it, including a concurrent request's response. A five-hour exhaustion and a
  weekly exhaustion are distinguishable only through the snapshot.
- An in-stream `error` event is reported to the result policy as `Success: true`.
  The router detects in-stream errors by parsing the stream.
- No SDK interface reports the account's paid-overflow setting before a request.
  Overage headers arrive only on responses.
- The header names and values come from the SDK parser and synthetic responses.
  Real Anthropic header shapes are pending the live lanes.

## Assignment storage

PR2 stores assignments in a single-writer, append-only JSON-lines journal.

- **Write rule.** `Assign` appends one record and calls `File.Sync` before it
  returns. Go issues `F_FULLFSYNC` on Darwin and `fsync` on Linux. A
  conversation's first record wins.
- **Concurrency.** One mutex serializes first assignments in the process. An
  exclusive `flock` on the state directory refuses a second process.
- **Recovery.** On open, replay every complete line. Truncate a torn final line
  left by a crash during append. Refuse to open when an interior line is
  corrupt, and report the error instead of reassigning.
- **Durability scope.** Acknowledged assignments survive a process crash. OS
  crash and power-loss durability rely on the platform fsync semantics above and
  are not tested.

A transactional embedded store, bbolt v1.5.0, also kept every acknowledged
assignment across the same kill -9 experiment. The journal won on size and speed:
it needs no dependency, committed about 11 times faster on the test host, and
reopened in under a millisecond. The comparison is in
`evidence/PR1/storage/storage-comparison.json`.

The initial component ships as a pinned source build.

- Prerequisite: Go 1.26.0 or later. PR1 used go1.26.8 darwin/arm64 from go.dev,
  archive sha256
  `a012b25b571bd0138a03dcd25375ceba866fe5ca822f426d2c66a4de56fd3f4b`.
- Dependencies come from `go.sum`. Prepare the module cache once with network
  access, then build and test with `GOPROXY=off GOSUMDB=off`.
- Prebuilt release binaries are out of scope for this program.

## SDK data races

The race detector reports data races inside the pinned SDK.

- **Configuration hot reload.** `Service.applyConfigRuntime` writes
  `BaseAPIHandler` fields that request handling reads without synchronization
  (`internal/api/server_reload.go:171`, `sdk/api/handlers/handlers.go:400` and
  `:411`). Pinned selection held in all 20 runs. The race detector fired in 4
  of 5 runs that sent requests right after the reload, and in none of the 5
  runs that waited for account state to settle first.
- **Startup model registration.** `Manager.ReconcileRegistryModelStates` writes
  auth state that `Auth.Clone` reads in the auth update queue and in
  `PrepareRequestAuth`. The race appeared in 1 of about 35 probe starts that
  loaded accounts before `Run`.

The probes avoid both races. They add accounts after start and wait until account
state settles (`Probe.WaitQuiet`). The default suite passes under `-race` with
that order. The hot-reload probe sits behind the `sdkreload` build tag.
